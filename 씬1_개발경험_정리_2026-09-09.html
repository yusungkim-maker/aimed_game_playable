01무엇을 만들었나 — 게임 요약

  → 코인 드롭 (RushGroup.coinDrop, 보스는 30)
  → 자석 반경 안이면 플레이어로 흡착

웨이브 트리

RushCycle은 몬스터가 다 죽기를 기다리지 않고 고정 간격으로 라운드로빈으로 계속 러쉬를 시작합니다. 이게 "끊기지 않는 압박"을 만드는 핵심이었습니다. RushConfig.nextRushName(전멸 후 연쇄)과는 별개 메커니즘입니다.

기본 2방향 루프
  → (유닛 소켓 마일스톤) 보스 1 + 3방향 영구 루프
  → (건물 트리거 2)      보스 3 + 6방향 x2 영구 루프
  → (건물 트리거 4)      보스 3 + 6방향 x3 영구 루프
  → (건물 트리거 6)      보스 6, 새 티어 없음
  → (건물 소켓 전부 완성) Rush_Final_Boss = 6경로 x 2보스 → 엔딩

Kingshot(경쟁작)에서 가져온 설계 원칙

  • 보스는 시간이 아니라 행동으로 나온다 — 코인 해금 완료, 용병 완충 같은 플레이어 행동이 트리거. 이 프로젝트의 소켓 트리거와 동일한 패턴.
  • 탑 수 x 탑당 용병 수 = 최대 추종자 수로 정확히 맞춤 (6탑 x 4명 = 24 = 최대 슬롯). "다 모으면 딱 다 채운다"는 페이싱 감각.
  • 코인은 해금에만, 배치는 무료 — 자원 단계와 배치 단계를 분리.
  • 주요 시설을 플레이어 사거리 밖에 배치해서 이동을 강제. 제자리에서 다 못 하게 만드는 동선 설계.
  • 단, 레퍼런스 데이터에 있어도 실제 플레이에 안 나오는 항목이 있었습니다(무기 제련 구역). 덤프 데이터를 100% 신뢰하지 말 것.

2026-09-09에 실제로 부딪힌 것 씬 2의 지면 텍스처를 바꾸면 씬 1의 지면도 같이 바뀝니다. 두 씬이 같은 에셋을 참조하기 때문입니다. 그런데 여기서 텍스처만 복제하는 건 소용이 없습니다 — MeshRenderer가 참조하는 건 텍스처가 아니라 머티리얼이고, 두 씬이 같은 머티리얼을 공유하는 한 그 머티리얼의 텍스처 슬롯을 바꾸는 순간 양쪽이 함께 바뀝니다. 머티리얼 → 텍스처, 둘 다 복제해야 분리됩니다.

게다가 지면 머티리얼은 ground.glb의 자동 생성 서브에셋(936b8821-…@b4e6b)이었습니다. 이런 머티리얼은 리임포트 때 재생성되므로 제자리 수정이 무의미합니다. 그래서 아래 순서로 처리했습니다 — 이 프로젝트에서 재사용할 표준 패턴입니다.

  1. 컴파일된 원본 머티리얼을 읽습니다 — library/93/<uuid>@b4e6b.json. 여기서 이펙트 uuid, _techIdx, _defines, _states(패스별 cullMode 포함), _props를 그대로 확보합니다. 인스펙터를 눈으로 보고 옮겨 적으면 {}(= 이펙트 기본값 사용)와 명시값의 차이를 놓칩니다.
  2. 텍스처를 복제 — asset_operations copy로 하면 편집기가 새 uuid와 .meta(redirect, 서브에셋 imageUuidOrDatabaseUri까지)를 정확히 생성해 줍니다. 손으로 .meta를 쓰지 마세요.
  3. 독립 .mtl을 생성 — asset_operations create에 1단계에서 읽은 JSON을 그대로 넣고 mainTexture만 새 텍스처 uuid로 바꿉니다.
  4. 컴파일 결과를 확인 — library/<uuid>.json을 다시 읽어 이펙트가 해석됐고 프로퍼티가 원본과 일치하는지 대조합니다.
  5. 렌더러에 할당 — _materials는 배열이라 MCP로 못 씁니다. 씬을 닫고 JSON 패치(7장 절차).
결과 (검증 완료) xp_np.scene의 ground → texture/Ground_xp_np.mtl → texture/ground_xp_np.png (전용)
scene.scene의 ground → ground.glb@b4e6b → texture/ground_new.png (기존, 그대로)
복제 텍스처는 픽셀 단위로 동일(97,439바이트 · 512²)하고 임포트 설정(repeat/repeat, mipfilter none, hasAlpha)도 같습니다. 이제 어느 쪽을 바꿔도 다른 쪽에 영향이 없습니다.
같은 함정이 남아있는 곳 — 씬 2에서 미리 확인할 것 ground_new.png는 rock.glb의 머티리얼도 함께 참조하고 있습니다(그래서 원본 텍스처는 아직 두 곳에서 쓰입니다). 지면 외의 배치물도 씬별로 다르게 하려면 같은 3단(텍스처 → 머티리얼 → 렌더러) 분리가 각각 필요합니다. 프리팹(Wall/Door/Tower)은 더 강하게 묶여 있습니다 — 프리팹 파일 자체가 공유되므로 머티리얼만 갈아도 두 씬의 모든 인스턴스에 반영됩니다. 씬별로 외형을 다르게 하려면 프리팹을 복제하거나 씬 인스턴스마다 머티리얼 오버라이드를 걸어야 합니다. 어느 에셋을 씬별로 분리할지 배치 전에 정해두는 게 훨씬 쌉니다.

05Cocos 엔진 함정 — 렌더 & 머티리얼

가장 값비쌌던 교훈 에셋 참조가 100% 정확한데도 메시가 안 보일 수 있습니다. 이 프로젝트는 UI_arrow.prefab이 안 보이는 문제로 며칠을 썼는데, 그동안 확인한 건 전부 "데이터 레이어"(메시/머티리얼/스켈레톤 참조)였고 진짜 원인은 "엔진 레이어"(셰이더 컴파일 실패)였습니다. 참조가 다 맞는데 안 보이면, 즉시 debug_debug_logs에서 "compilation failed"를 검색하세요. 셰이더 컴파일 실패는 에셋 레벨에서 아무 에러도 내지 않지만 엔진 레벨에는 항상 로그가 남습니다.
builtin-standard.effect가 이 엔진 버전에서 컴파일 실패합니다
증상
glTF 임포터가 자동 생성한 평범한 텍스처 머티리얼인데 메시가 아무것도 안 그려짐. 콘솔 에러 없음.
원인
정의 토큰에 CC_USE_REFLECTION_PROBE[object Object]가 들어가 GLSL이 깨집니다. 씬에 ReflectionProbe가 하나도 없는데 발생 — 프로브 0개 케이스의 엔진 매크로 계산 버그로 보입니다. 파이프라인 스테이트를 못 만들므로 렌더링이 아예 없습니다.
해법
엔진 버그를 고치려 하지 말고 builtin-unlit.effect로 교체하세요. 같은 텍스처, 같은 결과, 조명/프로브 경로를 아예 안 탑니다. 이 프로젝트의 NumberAtlas/FxHit/MapBoundsLine 전부 unlit입니다.
legacy/toon은 커스텀 .effect로 포크할 수 없습니다
증상
ERROR: 0:939: 'syntax error' : invalid expression
원인
builtin-toon.effect를 바이트 단위로 그대로 복사해도 동일한 에러가 납니다. 즉 내용 문제가 아니라, #include <surfaces/...> 청크 기반 이펙트를 새 에셋으로 등록하는 것 자체가 깨지는 엔진 버그입니다. legacy/standard, builtin-standard도 같을 것으로 봅니다.
해법
legacy/unlit으로 가세요. 단, 스키닝 메시라면 legacy/unlit의 기본 버텍스 청크(legacy/input)는 스키닝을 안 하므로 #include <legacy/input-standard>를 써야 합니다. 이게 CC_USE_SKINNING을 내부에서 처리해 줍니다. 이 프로젝트의 StructureHit.effect/GlowFx.effect/FollowerGhost.effect 전부 이 조합입니다.
모델 전체가 단색(검정 등)으로 칠해지는 두 가지 다른 원인

증상은 똑같습니다 — 아웃라인이 얇은 테두리가 아니라 모델 전체를 덮습니다. 원인은 둘이고 해법도 다릅니다. 둘 다 확인하세요.

원인 A — cullMode
legacy/toon의 USE_OUTLINE_PASS는 그 패스에 cullMode: front가 필요합니다. Blender에서 "Backface Culling"을 끄고 익스포트하면 임포트된 머티리얼의 모든 패스가 cullMode: 0 (none)이 되어 이펙트 자체 기본값을 덮어씁니다. 확장된 아웃라인 셸의 앞면까지 그려져 실제 표면을 완전히 가립니다. → 별도 .mtl을 만들어 패스 0의 rasterizerState.cullMode를 1(NONE=0, FRONT=1, BACK=2)로 명시.
원인 B — 단일축 음수 스케일
이건 Cocos 버그가 아니라 래스터화의 사실입니다. 한 축만 음수 스케일((0.7, 0.7, -0.5))이면 변환 행렬식이 음수가 되어 삼각형 와인딩이 뒤집히고, cullMode: front가 반대쪽을 컬링합니다. → 미러링을 음수 스케일로 하지 마세요. 메시가 그 축 기준으로 대칭이면 다른 축 180도 회전으로 시각적으로 동일한 결과를 얻을 수 있고, 회전은 행렬식이 항상 +1이라 와인딩을 깨지 않습니다.
구분법
먼저 아웃라인 패스의 실제 rasterizerState.cullMode를 읽습니다({}는 "이펙트 기본값 사용"이라는 뜻이니, 그 기본값이 무엇인지는 컴파일된 library/<uuid>.json에서 확인). 그게 이미 맞으면 그 노드와 모든 조상 노드의 _lscale에 음수 성분이 있는지 봅니다.
중첩 프리팹 함정
해당 노드가 다른 프리팹 안에 중첩돼 있고 그 외곽 프리팹이 그 노드의 프로퍼티를 한 번이라도 오버라이드한 적이 있으면, Cocos는 그걸 절대값 오버라이드로 기록해 원본 프리팹의 값을 완전히 대체합니다. 이미 오버라이드된 노드에 보정 회전을 넣으면 그 인스턴스에서는 조용히 무시됩니다. 아무것도 오버라이드하지 않는 조상/자손 노드를 골라 고치세요.
Material.getProperty → 캐시 → setProperty 라운드트립으로 복원하지 마세요
증상
히트 플래시가 한 번 켜지면 영구히 안 꺼짐.
원인
getProperty(name, passIdx)에 명시적 패스 인덱스를 주면, 그 패스가 해당 프로퍼티를 선언하지 않은 경우 null을 반환합니다(예: 멀티패스 툰 머티리얼의 패스 0은 emissive가 없는 아웃라인 패스, 진짜 표면은 인덱스 1). 그러면 if (captured != null) restore() 가드가 복원을 조용히 건너뜁니다.
해법
캡처/복원 왕복을 없애고, 셰이더 선언 기본값을 하드코딩해서(컴파일된 이펙트 JSON에서 한 번 읽어옴) 정리 시점에 무조건 setProperty를 호출하세요. 덧붙여 scheduleOnce/unschedule에는 같은 바인딩된 콜백 참조를 쓰세요 — 인라인 화살표 함수는 자기 자신과 매칭되지 않아 연타 시 타이머가 안 리셋됩니다.
setMaterial()에 이미 인스턴스화된 머티리얼을 넣으면 throw

cc.Graphics는 UI 배처 파이프라인으로 렌더되므로, UI 카메라 패스가 없는 비-Canvas 3D 노드에서 나올지가 불확실합니다. 대신 평면 쿼드 Mesh + MeshRenderer를 선분마다 쓰세요(중점에 배치, 한 축으로 length/2 스케일). 이미 게임의 다른 모든 이펙트가 통과하는, 검증된 3D 렌더 경로를 그대로 씁니다. MapBounds의 영역 외곽선이 이 방식입니다.
@executeInEditMode만으로는 디버그 비주얼이 실제 게임에서도 그려집니다
원인
@executeInEditMode는 "편집 중에도 추가로 틱한다"는 뜻일 뿐, update()는 Play/프리뷰/실제 빌드에서도 정상 실행됩니다. if (this.showDebugOutline) draw()는 디버그 지오메트리를 그대로 출시 빌드로 유출시킵니다.

06Cocos 엔진 함정 — 런타임 & UI 좌표계

update()는 애니메이션 시스템보다 먼저 돕니다 — 클립 끝 판정이 항상 한 프레임 늦습니다
증상
문 열림/닫힘 애니메이션 양 끝에서 정확히 한 프레임 반대 포즈가 번쩍입니다.
원인
Director.tick() 순서: before_update → _compScheduler.updatePhase(dt)(당신의 update()) → systems.update(dt)(애니메이션이 시간을 전진시키고 이 프레임에 렌더될 포즈를 샘플링) → lateUpdate → draw. 즉 update()에서 읽는 state.time은 지난 프레임 값이고, "아직 안 끝났네"라고 판단하면 엔진이 즉시 정지점을 지나쳐 그 오버슈트 포즈를 렌더합니다. WrapMode.Loop이면 오버슈트가 클립의 반대쪽 끝으로 감겨서, 살짝 지나친 포즈가 아니라 완전히 엉뚱한 포즈가 나옵니다.
해법
엔진에게 시간 소유권을 주지 마세요. state.speed = 0으로 고정하고 update()에서 state.time을 직접 범위 클램프하며 전진시킨 뒤 setTime + sample. 오버슈트가 불가능해지므로 업데이트 순서와 wrapMode 둘 다 무관해집니다. (클립을 자르거나 wrapMode를 바꾸는 건 증상만 줄입니다.)
Camera.convertToUINode()는 Canvas 노드의 월드 위치에 의존합니다
증상
월드에 붙는 UI(체력바 등)가 16:9에서는 완벽한데 세로로 길어질수록 위로 올라가 결국 화면 밖으로 나갑니다.
원인
내부적으로 월드 → 스크린 픽셀로 변환한 뒤, 원점이 화면 좌하단이고 view.getVisibleSize()를 span하는 "UI 월드 공간"의 점으로 만들고(tmp.y = cy / view.getScaleY() + 0.5 * visibleSize.height), 그 다음에야 convertToNodeSpaceAR()로 대상 노드의 월드 행렬을 뺍니다. 따라서 Canvas 노드는 항상 (visibleSize.w/2, visibleSize.h/2)에 있어야 합니다. alignCanvasWithScreen이 바로 이걸 유지해 주는데, contentSize/orthoHeight만 만지는 자체 핏 스크립트는 안 해 줍니다.
결정적 진단
오차가 디자인 종횡비에서 정확히 0이고, 종횡비가 벌어질수록 선형으로 커진다면 이겁니다. 이 프로젝트에선 Canvas가 (640,360)에 고정돼 있어서 16:9는 픽셀 단위로 정확했지만 9:16에서는 y가 약 1138이 필요했습니다 — +778 유닛 오차.
해법
자체 핏 스크립트가 Canvas 노드 위치까지 소유하게 하고, view.setDesignResolutionSize()도 호출해서 엔진의 visibleSize와 Canvas contentSize가 같은 스케일에 있게 하세요(이 프로젝트는 720 기준과 1280 기준으로 서로 어긋나 있었습니다).
한 번 잘못 고쳤다가 되돌린 것 2026-09-07에 UIAutoFit.ts를 삭제하고 내장 alignCanvasWithScreen에 맡기는 게 "근본 해결"이라고 판단했는데, 이 프로젝트에서는 그 경로가 실제로 동작하지 않아 2026-09-08에 되돌렸습니다. 최종 정답은 UIAutoFit을 쓰고 alignCanvasWithScreen은 OFF, 그리고 UIAutoFit이 Canvas 위치까지 책임지게 하는 것입니다. 둘을 동시에 켜면 절대 안 됩니다 — 같은 contentSize/orthoHeight를 서로 다른 공식으로 매 리사이즈마다 써서 마지막에 실행된 쪽이 비결정적으로 이기고 레이아웃이 두 답 사이에서 떨립니다. 소유자를 하나만 정하세요.
Widget.alignMode는 ALWAYS로

AudioSource에는 재생 속도/피치 API가 없습니다 (3.8)

오디오 스프라이트 운용

"재생 구간" API는 없으므로 구간 길이는 자체 타이머로 강제해야 합니다. 보이스를 풀링할 때는 각 재생에 토큰을 달고 정지 타이머가 토큰을 검사하게 하세요 — 안 그러면 재활용된 채널의 옛 타이머가 새 소리를 끊습니다. 이 프로젝트는 우선순위 기반 스틸링(building 3 > coin_ground 2 > coin 1 > arrow/monster-death 0)을 쓰고, 낮은 우선순위 소리는 버려지지 훔치지 않습니다.

커스텀 스크립트는 압축 CID로 직렬화됩니다

원시 타입 배열에는 type을 명시해야 합니다
@property({ ... }) rushNames: string[] = []처럼 type: [String] 없이 빈 배열 기본값으로 선언하면, 프로퍼티가 아예 등록되지 않습니다. 값이 비는 게 아니라 Object.keys()에서 사라집니다. CCClass가 배열 원소 타입을 기본값에서 추론하는데 빈 []는 추론할 게 없기 때문입니다. 컴파일 에러도, 경고도, 세터 실패도 없습니다 — 조용히 못 쓰는 프로퍼티가 됩니다. 항상 type: [String]/[Number]/[Boolean]을 명시하세요.

  2. "우연히 맞는 값"을 복사해 오지 마세요. 다른 노드에서 가져온 -45도 기울기가 특정 yaw 한 각도에서만 맞았고 다른 각도에서는 edge-on으로 사라졌습니다. 처음부터 유도하고, 라이브 노드 트랜스폼으로 교차 검증하세요(이 프로젝트에서는 두 정점 노드의 실제 worldPosition으로 계산한 중점/길이/각도가 자동 생성된 디버그 세그먼트와 소수점 4자리까지 일치했습니다 — 스크린샷 없이 검증 완료).
  3. 연쇄 에러의 첫 줄만 진짜입니다. setMaterial 실패의 두 번째 에러(localSetLayout)처럼, 뒤따르는 에러는 첫 에러가 중간에 중단시킨 결과일 뿐입니다. 마지막에 출력된 줄이 아니라 debug_debug_logs의 ERROR 레벨 첫 줄을 보세요.

성능 판단

몬스터 겹침 — 프레임당 추가 연산 0으로 해결
200마리에서 이미 프레임당 VirtualWall 검사가 약 7,600회 돌고 있었고, 이웃 스캔을 추가하면 200의 제곱 = 40,000회가 됩니다. 그래서 전부 스폰 시점으로 밀었고 이동 루프는 손대지 않았습니다.
  1. 레인 오프셋 — 경로 중심선에서 좌우로 비켜 걷게. 주의: 경로의 웨이포인트 목록은 그 경로의 모든 몬스터가 공유하므로 절대 in-place로 수정하면 안 됩니다. 몬스터별 사본을 만드세요. 문이 좁으므로(통로 약 1.8m) 끝으로 갈수록 laneTaper로 다시 좁힙니다.
  2. 속도 지터 ±12% — 속도가 같으면 한 번 뭉친 무리는 영원히 뭉쳐 다닙니다.
  3. 공격 사거리 지터 0~+35% — 최악의 겹침은 걸을 때가 아니라 모두 같은 반경에서 멈출 때 생깁니다. 바깥쪽으로만 넓히면 기지 안으로 파고들지 않습니다.
레인 값은 Math.random()이 아니라 황금비 저불일치 수열(seq = (seq + 0.618...) % 1)로 뽑습니다 — 랜덤은 연속 스폰에서 실제로 뭉칩니다(12연속 스폰이 좌 6 / 우 6으로 갈리는 것 확인).
보류: 그리드 기반 밀어내기(2단계, 균일 그리드로 프레임당 약 1,600회). 위 세 가지가 부족할 때만 꺼내고, 순진한 O(n제곱) 스캔은 절대 하지 마세요.
그림자 — 전체 적용에서 되돌렸습니다
처음엔 "씬의 모든 것"에 그림자를 켰는데, 몬스터 40마리 이상 + CSM-4 동적 그림자가 랙 요인으로 지목되어 플레이어 · 팔로워 · 건물만으로 좁혔습니다. 나머지는 껐습니다.
참고: 이미 클래스 기본값(0)인 프로퍼티를 세터로 0으로 되돌리면 명시적 0을 쓰는 게 아니라 오버라이드가 제거됩니다 — 같은 결과에 파일이 더 깔끔합니다.

빌드 & 배포 (플레이어블 광고)

  • MRAID 계열 채널(AppLovin/Unity/Liftoff) 익스포트는 <script src="mraid.js">를 무조건 <head>에 주입합니다. 이건 광고 네트워크의 SDK 파일이고 개발자가 번들하지 않으므로, 익스포트된 HTML을 로컬/일반 브라우저에서 열면 항상 스플래시에서 멈춥니다. 프로젝트 버그가 아닙니다. 로컬 테스트용으로는 build/mraid.js에 최소 스텁을 두면 됩니다(스크립트 태그가 상대 경로라 정확히 같은 폴더에 있어야 합니다).
  • file://로 열면 별개의 이유로 실패합니다 — Chrome의 "file: URL은 각각 고유 오리진" 정책이 엔진의 blob/모듈 기반 에셋 로더를 깨서 Error 3702가 연쇄합니다. 항상 실제 로컬 HTTP 서버로 서빙하세요. 파일을 그냥 건네주거나 더블클릭으로 되길 기대하면 안 됩니다.
  • 내장 물리를 전혀 쓰지 않습니다(RigidBody/Collider/PhysicsSystem/레이캐스트 전무). Feature Cropping에서 3D Physics와 2D box2d를 끄면 빌드 용량이 확실히 줄어듭니다(ammo/bullet WASM이 큽니다). 아직 실제로 끄지 않았습니다 — MCP 세터가 없어 사람이 해야 합니다.
  • 유령 uuid 문제: 편집기 밖에서 파일을 rename/replace하면 library 캐시에 uuid→경로 항목이 남고, 지금 어떤 소스도 그 uuid를 참조하지 않는데도 빌드 번들 매니페스트가 끌어와 Error 3702가 납니다. 해법은 편집기를 닫고 library/ + temp/ 삭제 후 재오픈(전체 클린 리임포트). 편집기가 닫혔는지는 server_server_connectivity 실패로 확인합니다(CocosDashboard.exe가 작업 목록에 남아 있는 건 런처일 뿐 무의미). 단, 그 역은 성립하지 않습니다 — 2026-09-09에 connectivity가 0ms로 응답하는데 씬 프로세스는 죽어 있는 경우를 확인했습니다.
