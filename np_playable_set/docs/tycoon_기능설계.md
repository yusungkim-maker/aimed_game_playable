## 0. 자원 모델 【확정】

| 자원 | 등 뒤에 실림 | 우측 상단 UI | 비고 |
|---|:---:|:---:|---|
| **나무** Wood | O | O | |
| **철** Iron | O | O | |
| **칼** Sword | O (상한 **50개**) | X | 등에만 보인다. 장부에도 안 센다 |
| **코인** Coin | X | O | 먹으면 개수만 올라간다 |

### 여기서 나오는 구조적 결론

**"등에 보이는 것"과 "개수로 세는 것"은 서로 독립된 축이다.** 칼은 보이지만 안 세고, 코인은 세지만 안 보인다.

현재 코드는 이 둘이 **하나로 붙어 있다** — `CoinStack.count`가 곧 보유량이고 `CoinCounterUI`가 그걸 읽는다. 그래서 그대로는 표현이 안 된다.

→ **축을 둘로 분리한다.**

**`CoinStack`을 "플레이어 인벤토리"로 만들고, 자원마다 세 가지를 따로 정한다.**

```
CoinStack (등 뒤 = 인벤토리)
   자원마다 →  등에 보이기 ?   몇 개까지 보일까 ?   몇 개까지 가질까 ?
   ────────────────────────────────────────────────────────────────
   나무        O               100 (넘으면 숫자만)   무제한
   철          O               100                   무제한
   칼          O               50                    50  ← 실제 보유 상한
   코인        X (숫자만)      —                     무제한
```

개수를 세는 곳이 **여기 한 군데뿐**이라 두 수가 어긋날 일이 없다. 우측 상단 UI는
`countOf(자원)`을 읽어 표시하고, 칼은 UI를 안 만들면 그만이다.

> 씬 1·2는 이 목록이 비어 있어 예전처럼 "코인 한 종류, 한 줄, 상한 없음"으로 동작한다.

## 1. `ResourceType` — 자원 타입 도입

```ts
// assets/scripts/ResourceType.ts  (TriggerId.ts와 같은 위치·형태)
export enum ResourceType {
    Coin  = 0,   // <- 기본값. 기존 씬·기존 호출은 전부 여기로 떨어진다
    Wood  = 1,
    Iron  = 2,
    Sword = 3,
}
```

**`Coin = 0`이 핵심이다.** 새로 추가되는 인자·필드의 기본값이 전부 0이 되어 **씬 1·2가 한 글자도 안 바뀐다**(규칙 5).

### 1-1. 바꿔야 하는 곳 (전부 "추가"이고 기존 동작은 유지)

| 파일 | 변경 | 씬 1·2 영향 |
|---|---|---|
| `CoinEvents.ts` | `ResourceDropped` payload에 **4번째 인자** `type` 추가 | 없음 — 기존 emit은 3개만 보내 `undefined` → `Coin` |
| `Coin.ts` | `resourceType` 필드 추가 (스폰 시 주입) | 없음 — 기본 `Coin` |
| `CoinPool.ts` | 타입 → 프리팹 표 추가. **표가 비면 기존 `coinPrefab`** | 없음 |
| `CoinStack.ts` | 타입별 레인 + `popTop(type)` | 없음 — 한 종류만 들어오면 레인 1개 |
| `CoinGroundStack.ts` | `acceptedType` 추가 (기본 `Coin`) | 없음 |
| `Choppable.ts` | `dropResourceType` 추가 (기본 `Coin`) | 없음 |
| `Socket.ts` | `requiredResource` 추가 (기본 `Coin`) | 없음 |

> 전부 **공유 코드**다. 손대고 나면 **규칙 10대로 씬 1·2를 반드시 실행 확인**한다.

### 1-2. ~~`ResourceLedger`~~ — 만들지 않았다 (설계 변경, 2026-09-17)

처음에는 "개수를 세는 장부"를 따로 두려 했으나, **칼은 장부에 세지 않는다**는 답을 듣고 다시 보니
**필요가 없었다.**

- 플레이어가 가진 나무·철·칼의 개수 = **등에 실린 개수 그 자체**다. (창고의 나무는 창고 쪽 `CoinGroundStack`이 센다. 상점의 칼 재고도 상점 소켓이 센다.)
- 코인은 등에 안 보일 뿐 같은 획득 경로를 탄다 → **"보이기"만 끄면 같은 자리에서 세어진다.**

→ **`CoinStack`을 "플레이어 인벤토리"로 만들고 끝냈다.** 개수를 세는 곳이 한 군데뿐이라 두 수가 어긋날 일이 없다.

### 1-3. 등 뒤 레인 【설계】

`CoinStack`이 타입마다 **자기 줄**을 갖는다. `CoinGroundStack`이 이미 2x2 레인을 쓰고 있으므로 같은 패턴이다.

```
등 뒤에서 본 모습 (레인 3개)
   [나무] [철] [칼]
     ▢     ▢    ▢
     ▢     ▢
     ▢
```

- 레인 간격·시작 오프셋은 인스펙터 노출.
- 레인이 1개뿐인 씬(1·2)은 지금과 동일한 한 줄.
- `popTop(type)`으로 소켓이 원하는 자원만 뽑아간다.

**상한은 두 종류가 따로 있다** — 헷갈리면 안 된다.
- **최대 표시 개수**(기본 100): 이 개수를 넘으면 **노드를 더 안 만들고 숫자로만 센다.** 개수 자체는 잃지 않으므로 소켓에 전부 넣을 수 있다. 등 뒤에 수백 개가 쌓이면 드로우콜이 그만큼 늘어 모바일에서 바로 렉이 된다.
- **보유 상한**(0 = 무제한): 개수 자체의 상한. **칼만 50개**이고 나무·철은 무제한이다.

### 1-4. 우측 상단 UI

- `CoinCounterUI`에 **`자원 종류로 거르기`** 를 추가했다. 끄면 예전처럼 **전부 합친 개수**를 보여준다(기본값 → 씬 1·2 무영향).
- 켜면 `표시할 자원`으로 무엇을 셀지 고른다 — `CoinStack.countOf(type)`을 읽는다.
- 씬 3: 나무·철·코인 3칸을 `Widget`으로 우측 상단에 배치. **칼 칸은 안 만든다.**

## 2. 소켓 A — `SpawnerSocket` (서 있으면 시간당 일꾼 배출)

기존 소켓은 전부 *"코인을 N개 채우면 1회 보상"* 이라 그대로 못 쓴다. **새 컴포넌트**를 만든다.

### 동작

```
매 프레임:
  플레이어가 발동 반경 안에 있나?
    예   -> 타이머 += dt
            타이머 >= 배출 주기 && 현재 일꾼 수 < 동시 상한
               -> 일꾼 1명 스폰, 타이머 -= 배출 주기
    아니오 -> (설정에 따라) 타이머 유지 또는 0으로 리셋
게이지 = 타이머 / 배출 주기
```

### 인스펙터 (전부 한글 displayName + 트레이드오프 tooltip)

| 프로퍼티 | 기본 | 설명 |
|---|---|---|
| 일꾼 프리팹 | null | **비어 있으면 아무 일도 안 한다**(무동작 원칙) |
| 배출 주기(초) | 3 | 짧을수록 빨리 늘지만 일꾼이 많아지면 프레임이 먹힌다 |
| 동시 상한 | 5 | 0이면 무제한 — 렉의 원인이라 툴팁에 명시 |
| 발동 반경(m) | 1.5 | 너무 크면 지나가기만 해도 나온다 |
| 자리를 비우면 | 진행도 유지 | 유지/리셋 선택. 리셋은 더 빡빡한 게임감 |
| 캐는 자원 | Wood | 이 소켓이 배출하는 일꾼이 무엇을 캐는가 |
| 게이지 노드 | null | 기존 `SocketGauge` 재사용 |
| 등장 위치 | null | 비우면 소켓 자신의 위치 |

### 왜 `Socket.repeatable`을 안 쓰는가

`repeatable`은 *"코인을 채우면 리셋되어 또 받는다"* 이지 *"서 있으면 시간이 찬다"* 가 아니다. 발동 조건 자체가 달라서 기존 클래스에 불리언을 더하면 **조건 분기가 두 겹으로 얽힌다**(코드 컨벤션: 불리언 플래그 덧붙이기 지양). 별도 컴포넌트가 맞다. 【설계】

### 일꾼 2종을 코드 한 벌로

`CoinCourier.harvestFromTrees`는 지금 *"가장 가까운 `Choppable`"* 을 찾는다. 여기에 **자원 타입 필터**만 더하면 광산도 같은 코드로 돌아간다.

```
Choppable.dropResourceType = Wood  -> 나무
Choppable.dropResourceType = Iron  -> 광산   <- 광산도 Choppable의 한 형태로 만든다
CoinCourier.harvestResourceType    -> 내가 캘 자원
```

**광산에 새 클래스를 만들지 않는다.** 【설계】

## 3. 대장간 합성 — `Forge` 【확정 기획 / 설계 제안】

> 사용자 지시: *"두 개의 소켓에 쌓을 수 있고, 쌓여진 소켓에 최소 나무 1개 철 1개가 들어가면 두 재료를 합성해서 하나의 칼로 뱉어내는 시스템"*

### 구조

```
입력 소켓 A (나무)  ┐
                    ├-- 둘 다 >= 소비량 이면 -> 소비 -> 칼 1개 산출 -> 산출 무더기
입력 소켓 B (철)    ┘
```

- 입력 소켓 = `CoinGroundStack` + `acceptedType`. **새로 안 만든다.**
- 산출 무더기도 `CoinGroundStack`(`acceptedType = Sword`). 플레이어가 다가가면 등으로 흡수되는 기존 경로를 그대로 탄다.

### 인스펙터

| 프로퍼티 | 기본 | 설명 |
|---|---|---|
| 입력 A / 입력 B | null | `CoinGroundStack` 2개. **하나라도 비면 무동작** |
| 소비량 A / B | 1 / 1 | 기획 확정치. 바꾸면 난이도 조절 |
| 산출 자원 | Sword | |
| 산출 개수 | 1 | |
| 합성 간격(초) | 1 | 0이면 프레임마다 시도 — 재료가 많으면 순식간에 다 갈린다(툴팁 명시) |
| 산출 무더기 | null | 비면 무동작 |
| 합성 이펙트 | null | 비면 연출 없이 동작 |

### 왜 "나무+철→칼"을 하드코딩하지 않는가

프로젝트 목표가 **재사용 모듈 라이브러리**다. 입력 2종·산출 1종의 일반 합성기로 두면 다음 광고에서 재료만 바꿔 쓴다. 코드량 차이는 없다. 【설계】

## 5. 레일 — UV 스크롤에 대한 답 【질문에 대한 답변】

### 결론: UV 스크롤이 맞는 접근이다. 다만 CPU가 아니라 셰이더에서 시간을 읽어라.

### 5-1. 왜 CPU로 `tilingOffset`을 돌리면 안 되는가

`builtin-unlit`에는 이미 `tilingOffset`(vec4, `.xy`=타일링 `.zw`=오프셋)이 있어서 매 프레임 `.zw`만 바꾸면 스크롤이 된다. **문제는 CPU 비용이 아니라 배칭이다.**

> `MeshRenderer.material` 게터는 **컴포넌트마다 `MaterialInstance`를 지연 생성한다**(CLAUDE.md 기록). 레일 조각마다 머티리얼이 갈라지면 **드로우콜이 조각 수만큼 늘어난다.** 레일이 20조각이면 드로우콜 +20이다.

CLAUDE.md의 성능 원칙 그대로다 — *"실제 랙의 1순위는 스크립트가 아니라 그림자·드로우콜·반투명 오버드로"*.

### 5-2. 권장 — `cc_time`을 읽는 커스텀 이펙트 1장

**엔진 소스 실측(2026-09-17):** `builtin-unlit.effect`의 버텍스 셰이더는 이미 `#include <builtin/uniforms/cc-global>` 을 하고 있어 `cc_time`을 **추가 작업 없이 바로 쓸 수 있다.**

```glsl
// builtin-unlit 을 복사해 만든 RailScroll.effect 의 vert()
v_uv = a_texCoord * tilingOffset.xy + tilingOffset.zw;
v_uv += scrollDir * cc_time.x * scrollSpeed;   // <- 이 한 줄
```

| | CPU 방식 | `cc_time` 방식 |
|---|---|---|
| 프레임당 CPU | 레일 수만큼 uniform 쓰기 | **0** |
| MaterialInstance | 조각마다 생성 | **안 생김** |
| 드로우콜 | 조각 수만큼 쪼개짐 | **1장 공유 → 배칭 유지** |
| 속도 런타임 변경 | 쉬움 | 머티리얼 1장의 uniform을 1회만 바꾸면 전체가 같이 바뀜 |

레일이 **전부 같은 속도로 돈다면** `cc_time` 방식이 모든 면에서 낫다. 구간별로 속도가 달라야 하면 머티리얼을 구간 수만큼(2장) 만들면 된다 — 조각 수가 아니라 **구간 수**만큼이다.

### 5-3. 함정 — `cc_time.w`를 믿지 말 것 (실측)

엔진 주석은 이렇게 적혀 있다:

```
vec4 cc_time; // ... w: fractinal part of x, better precious, should be used with uv animation
```

"UV 애니메이션에는 `.w`를 써라"는 말이다. **그런데 3.8.8 구현은 그렇지 않다:**

```ts
// cocos/rendering/pipeline-ubo.ts:66
fv[TIME_OFFSET + 3] = root.cumulativeTime - Math.floor(root.frameTime);
```

`frameTime`은 **프레임 델타**(약 0.016초)라 `Math.floor()`가 **항상 0**이다. 즉 **`cc_time.w`는 사실상 `cc_time.x`와 같은 값**이고, 주석이 약속한 정밀도 이득은 없다(`cumulativeTime`을 floor했어야 하는 자리로 보인다 — 【추론】).

→ **`cc_time.x`를 쓰면 된다.** 플레이어블 광고는 길어야 60초라 float 정밀도가 문제되는 구간에 도달하지 않는다.

### 5-4. 레일 위를 흐르는 "자원"은 별개다

레일 표면 스크롤은 *"벨트가 돌아간다"* 는 배경 연출이다. **자원이 옮겨진다**는 것을 보여주려면 그 위를 실제 오브젝트가 지나가야 한다. 기획이 "창고→대장간으로 옮긴다"이므로 **둘 다 필요할 가능성이 높다.** 【설계】

- 자원 오브젝트는 **반드시 풀링**한다(`CoinPool` 패턴). 개체 수가 곱해지는 지점이다.
- 도착하면 목적지 `CoinGroundStack`에 들어간다 — **기존 경로 재사용**, 새 이동 로직 없음.

### 5-5. 검토했지만 버린 대안

| 대안 | 왜 버렸나 |
|---|---|
| PNG 시퀀스 아틀라스 | 프레임 수만큼 텍스처가 커진다. 5MB 규격에서 손해. UV 스크롤은 용량 0 |
| 본 애니메이션으로 벨트 회전 | 스켈레톤 비용 + 조각마다 `SkeletalAnimation`. 가장 비싸다 |
| 머티리얼 스왑 | 프레임마다 머티리얼 교체 — 배칭이 매 프레임 깨진다 |

## 6. 광산 【대기】

사용자가 에셋을 정리해 넣은 뒤 착수한다. 설계 방향만:

- **`Choppable`의 한 형태**로 만들어 채집 코드를 재사용한다(2절 참조).
- 철 자원 오브젝트는 `T_Wood.prefab` 구조를 그대로 따른다 — **크기는 루트가 아니라 자식 노드에 준다**(`Coin._updatePop()`이 루트 스케일을 1.0으로 덮어쓴다).

### 씬 3에서 인스펙터로 채워야 하는 것

코드는 준비됐지만 **씬 데이터가 비어 있어 아직 아무 동작도 안 한다.**

- `Player`의 `CoinStack` → **자원 레인 목록**에 4줄 (나무/철/칼/코인). 칼은 보유 상한 50, 코인은 "등에 보이기" 끄기
- `CoinSystem`의 `CoinPool` → **자원별 프리팹**에 나무·철·칼 프리팹
- `T_Tree`의 `Choppable` → **뱉는 자원 = 나무**
- `Warehouse`의 `CoinGroundStack` → **받는 자원 = 나무**
- 우측 상단 UI 3칸 → `CoinCounterUI`의 **자원 종류로 거르기** 켜고 종류 지정

> 배열 프로퍼티(`자원 레인 목록`, `자원별 프리팹`)는 **MCP로 못 쓴다** — 인스펙터 또는 씬 JSON 패치가 필요하다.
