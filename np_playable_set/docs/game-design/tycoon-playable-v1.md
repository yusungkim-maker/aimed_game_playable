## 1. 게임 기획과 목적

### 1.1 한 문장 컨셉

**내가 벤 나무가 건물이 되고, 그 건물에서 나온 일꾼이 나 대신 나무를 캐서, 더 큰 기지를 열어 준다.**

플레이어의 역할이 **벌목꾼 → 첫 고용주 → 자동화 기지 운영자**로 바뀌는 순간을 짧게 체험시킨다. 핵심 판매 포인트는 자원 수량 자체보다 **같은 시간에 내 기지가 해내는 일이 늘어나는 모습**이다.

| 항목 | v1 제안 |
|---|---|
| 장르 / 방향 | 채집으로 시작해 건설·확장·자동화를 체험하는 아케이드 타이쿤 |
| 첫 체험 대상 | 복잡한 경영 메뉴보다 이동·수집·눈에 보이는 성장을 좋아하는 캐주얼 이용자라는 가설 |
| 광고 목표 | 첫 조작을 유도하고, 자동화의 가치를 체험시킨 뒤 설치 의향을 만든다 |
| 조작 | 한 손 드래그 이동. 가까운 나무 자동 벌목·자원 자동 획득·건설 구역 자동 납품 |
| 카메라 | 기존 고정 각도 오소그래픽 기준. 필요할 때 위치·줌만 보정 |
| 길이 | 첫 조작 이후 정상 경로 45~60초, 능숙한 플레이는 더 빨리 완료 가능 |
| 재화 | 목재 1종. 코인·보석·식량·돌·가공 판자는 v1에서 0종 |
| 성장 | 필수 투입 4회, 지도 확장 1회, 일꾼 0→1→2명 |
| 전투 | 몬스터 0마리. 플레이어 HP·전투 공격력·기지 피격 시스템 없음 |
| 채집 판정 | 나무 내구도 3, 도끼 채집력 1, 3회 타격으로 목재 6개 |
| 정서 | 편안한 정리감, 쌓이는 만족감, 내가 만든 변화에 대한 주도권 |
| 결말 | 자동 생산이 가속된 것을 확인하고 다음 구역의 가능성을 본 뒤 설치 CTA |

숲·지면은 현재 아트 방향에 맞춘다. 설원, 눈 파티클, 날씨 시스템은 이번 요구에서 확정되지 않았으므로 추가 제작의 전제로 삼지 않는다.

### 1.2 명확한 후킹 포인트

| 순간 | 화면에서 실제로 보이는 것 | 기대하는 감정 / 검증할 가설 |
|---|---|---|
| 첫 조작~3초 | 나무가 흔들리고 통나무 6개가 등으로 연속 흡수됨 | 작은 행동에 충분히 큰 결과가 생겨 조작을 계속한다 |
| 5~7초 | 등에 있던 나무가 비어 있던 기지에 들어가 건물이 완성됨 | 자원이 화면을 바꾸는 원인임을 이해한다 |
| 15~18초 | 오두막에서 첫 일꾼이 나와 나무를 캐고 운반함 | 내가 하던 일을 다른 캐릭터가 대신한다는 변화를 읽는다 |
| 24~30초 | 빈 경계 너머에 길과 두 번째 생산 구역이 연결됨 | 다음 확장의 목적을 눈으로 이해한다 |
| 42~52초 | 두 일꾼의 등짐과 저장소 납품이 연이어 발생함 | 기지가 살아 움직이며 생산량이 늘었다고 느낀다 |

**가장 중요한 장면은 첫 일꾼의 첫 납품이다.** 고용 숫자만 바꾸거나 일꾼이 나오자마자 광고를 끝내면 자동화라는 약속을 체험시키지 못한다. 벌목·운반·저장고 증가가 같은 화면에서 인과관계로 이어져야 한다.

### 1.3 비교한 방향과 선택 이유

| 방향 | 장점 | 이번 제작 조건에서의 부담 | 판단 |
|---|---|---|---|
| 채집→판매→코인→건설 | 거래·수익 표현이 직관적 | 두 재화, 판매처·손님·환전 단계 추가 | 다음 변형안으로 보류 |
| 채집→건설→방어 | 위협과 성장의 목적이 선명 | 몬스터·전투·HP·실패 처리, 디펜스 쪽으로 초점 이동 | v1 제외 |
| 채집→건설→일꾼→확장 | 현재 준비물과 맞고 자동화 보상이 직접적 | 일꾼의 생산·납품을 명확하게 연결해야 함 | **v1 채택 제안** |

목재 1종으로도 획득·소비·생산 증가·영토 확장을 모두 표현할 수 있다. 가공소는 목재 생산을 개선하는 시설로 설정하고, 별도 판자 재화를 만들지 않는다.

## 2. 최근 공개 사례에서 가져올 것

### 2.1 조사 범위와 근거 수준

조사일은 2026-09-16이다. 확인 가능한 2025년 광고 분석, 2025년 말 제작사 UX 가이드, 현재 공개된 킹샷 플레이어블 분석을 참고했다. **2026년 전체 집행 소재를 전수 조사하거나 킹샷의 내부 전환 데이터를 확보한 것은 아니다.** 아래 영상 사례를 실제 HTML 플레이어블의 조작 내용으로 바꿔 서술하지 않는다.

### 2.2 빌려올 원칙

1. 설명보다 먼저 손으로 작은 성공을 만든다.
2. 얻은 자원을 눈앞의 변화와 연결한다.
3. 이미 배운 행동으로 다음 보상을 얻을 수 있게 한다.
4. 초반과 후반의 화면 차이를 크게 만든다.
5. 방금 얻은 보상을 충분히 보여주고, 그 너머에 다음 목표를 남긴다.

## 3. 플레이어블의 시작부터 끝까지

### 3.1 첫 화면

주인공, 바로 앞 나무, `목재 0/6`인 기초 건설 구역이 동시에 보인다. 빈 기지 뒤에는 두 번째 오두막의 낮은 실루엣과 연결 전 도로가 보인다. 잠긴 먼 구역은 흐린 색으로만 표현한다.

첫 문구는 **‘나무를 모아 기지를 세우세요’**. 손가락 가이드는 시작점에서 첫 나무 방향으로 짧게 한 번 이동하고 사라진다. 첫 터치는 이동으로 처리한다. 첫 입력 전에는 생산·벌목·진행 시간 측정이 시작되지 않는다.

| 첫 입력 후 목표 시간 | 단계 | 플레이어 행동 / 필요량 | 즉시 보상 | 다음 행동 유도 |
|---|---|---|---|---|
| 0~3초 | 첫 채집 | 첫 나무를 3회 타격, 목재 6개 수집 | 나무 흔들림, 쓰러짐, 등짐 6개 | 첫 건설 구역 0/6 강조 |
| 3~7초 | S1 기지 창고 | 목재 6개 납품 | 비어 있던 기초→작은 창고. 저장 기능 개방 | 오두막 구역 0/12 표시 |
| 7~18초 | S2 벌목 오두막 | 나무 2그루 상당, 목재 12개 납품 | 일꾼 1명 합류·자동 벌목 시작 | 확장 구역 0/18 표시 |
| 18~30초 | S3 진입로 확장 | 기준 경로: 직접 목재 12개 + 일꾼 6개 | 경계가 열리고 길이 연결됨. 새 생산 구역 공개 | 가공소 구역 0/24 표시 |
| 30~45초 | S4 가공소 완성 | 기준 경로: 직접 6개 + 일꾼 18개 | 일꾼 2명, 각 일꾼 운반량 증가, 기지 Lv.3 연출 | 두 생산 경로와 저장량 증가를 함께 노출 |
| 45~52초 전후 | 자동화 보상 확인 | 추가 결제 없이 움직이거나 관찰 | 두 일꾼이 각각 한 차례 이상 납품 | ‘이제 기지가 스스로 자랍니다’ |
| 성공 조건 충족 후 | 소프트 엔드카드 | 배경은 계속 동작, CTA 선택 가능 | 더 큰 구역의 실루엣과 확장 예고 | ‘더 큰 기지 만들기 · 설치’ |

시간은 예상 동선에 따른 목표값이다. **시간만 지나면 건설되는 구현을 하지 않는다.** 실제 진도는 자원 납품·건물 완성 이벤트로 진행한다. 빠른 이용자는 성공 조건을 빨리 달성할 수 있다.

### 3.2 배치 기준

고정 좌표를 새로 강요하지 않고 아래 동선 거리를 기준으로 현재 씬에 맞춘다. 세계 단위는 기획상 가정이며 기존 캐릭터·맵 스케일이 다르면 이동 시간에 맞춰 환산한다.

```text
          [다음 기지 실루엣 — v1에서 진입하지 않는 예고]
                   [가공소 S4]
               [두 번째 일꾼 작업 구역]
                       ↑
                [진입로 확장 S3]
                       ↑
 [플레이어 채집 구역]   [창고 S1]   [오두막 S2 + 일꾼 작업 구역]
          ↑
      [플레이어 시작]
```

- 시작→첫 나무: 이동 0.3~0.5초. 나무→첫 건설 구역: 1~1.5초.
- 주요 목표 사이 이동: 편도 1~2초, 가급적 3~6 세계 단위.
- 한 시점에 활성 납품 구역은 1개. 다음 목표는 실루엣만 보여준다.
- 일꾼의 왕복 경로는 플레이어 통로와 교차하지 않도록 분리한다.
- 첫 일꾼의 작업 위치·저장소·다음 납품 구역은 같은 화면에 배치한다.
- 확대·축소 시 카드의 투영 각도는 고정한다. 카메라 회전으로 2D 건물 뒷면이 보이지 않게 한다.
- 세로와 가로 화면 모두 현재 목표와 플레이어가 보이게 맞춘다. ‘세로 전용’으로 출고하지 않는다.

### 3.3 종료 규칙

정상 성공은 S4 완성, 그 이후 두 일꾼 각각의 실제 납품 1회 이상, 완성 후 최소 6초의 보상 노출을 모두 만족한 시점이다. 미리 준비한 가짜 목재를 넣어 성공을 연출하지 않는다. 최대 2명이며, 추가 군중은 필요 없다.

엔드카드는 화면 일부를 쓰는 패널이다. 배경 생산과 이동은 유지하고 새 필수 건설은 열지 않는다. 다음 구역은 클릭 가능한 가짜 건설 버튼이 아닌 잠긴 미리보기다. 설치 버튼은 명시적인 별도 터치에서만 동작한다.

진행이 느려 **첫 입력 이후 활성 플레이 70초**를 넘으면 현재 기지를 배경으로 ‘이어서 기지를 키워 보세요’ CTA를 보조 노출한다. 성공했다고 거짓 표시하지 않으며, 게임 진행은 계속 가능하다. 숨김·백그라운드 시간은 이 70초에 포함하지 않는다. 이 시간은 제품 설계값이며 광고 SDK의 종료·닫기 타이머를 제어하지 않는다. 본 초안은 일반 HTML 플레이어블용이며 별도 짧은 지면은 집행 규격 확인 후 압축한다.

## 4. 재화·수치·경제 설계

숫자 원본은 동봉한 `tycoon-balance-v1.json`이다. 엔진에 바로 임포트되는 설정 파일이 아니라 Claude가 인스펙터 설정으로 매핑할 기획 데이터다.

### 4.1 재화 종류와 소유권

**소비 재화는 목재 1종이다.** 등짐, 땅의 드롭, 창고의 목재는 같은 재화의 서로 다른 보관 위치다. 인구·기지 레벨·생산량은 상태 표시이며 비용으로 쓰지 않는다.

| 저장 위치 | 논리 용량 | 비주얼 / 사용 규칙 |
|---|---:|---|
| 플레이어 등짐 | 12개 | 최대 12개 표시. 2그루를 캐면 가득 참 |
| 일꾼 등짐 | 기본 6개, 업그레이드 후 12개 | 초기 일꾼은 6개, 업그레이드 후 최대 12개 |
| 창고 | 120개 | 저장량 숫자는 정확하게, 쌓인 모델은 최대 8개로 요약 |
| 땅의 목재 | 전역 드롭 노드 최대 24개 | 생성 예산이 부족하면 새 벌목 시작을 보류. 자원 삭제 금지 |
| 건설 납품 | 각 비용 한도 | 투입 즉시 소비, 중간에 나가도 진행량 보존 |

HUD에는 ‘운반 8/12’, S1 이후 ‘창고 6’을 구분한다. 합계만 보여 플레이어가 등짐과 창고를 이중 계산하게 만들지 않는다. 건설 구역에는 납품 완료량/가격만 보여준다.

납품 구역에서 멈추면 플레이어 등짐을 먼저 쓰고 부족분은 창고에서 쓴다. 창고 납품도 짧은 통나무 이동 효과로 출처를 보여준다. **일꾼은 창고에만 납품한다. 플레이어가 건설 구역을 방문해야 건설 지불이 진행된다.** 자동화가 플레이어의 건설 선택을 대신하지 않는다.

### 4.2 기본 수치

| 변수 | 초기 제안값 | 목적 |
|---|---:|---|
| 이동 속도 | 4 세계 단위/초 | 주요 편도 이동 1~2초 목표. 실제 스케일에 맞춰 환산 |
| 나무 내구도 / 채집력 | 3 / 1 | 세 번의 타격으로 한 번의 명확한 보상 |
| 타격 간격 | 0.45초 | 첫 타격 예열 0.15초, 이후 두 번의 간격으로 약 1.05초 벌목 |
| 벌목 반경 | 1.2 세계 단위 | 범위 내 최근접 1그루. 한 번에 여러 그루 타격 안 함 |
| 수집 반경 / 흡수 시간 | 1.6 단위 / 0.25초 | 흩어진 목재 줍기 위해 되돌아가는 일 최소화 |
| 나무 1그루 생산 | 목재 6개 | 비용이 6의 배수여서 읽기 쉬움 |
| 납품 속도 | 0.10초당 1개 | 6개는 0.6초, 24개도 2.4초 안에 보상 |
| 건설 완성 연출 | 0.6초 | 기다리는 시간이 아니라 완성 피드백 |
| 일반 나무 재생성 | 소진 후 8초 | 10그루 수동 경로 및 장시간 플레이도 고갈 방지 |
| 안내 재노출 | 진행·이동 없이 4초 | 손가락/화살표만 재표시, 자동 결제나 강제 이동 없음 |
| 첫 일꾼 | 6초당 6개 | 평균 1개/초. 첫 납품은 고용 후 약 6초 |
| 가공소 업그레이드 후 | 2명 × 각 6초당 12개 | 평균 합계 4개/초. 이전 대비 총 생산 4배 |

위 채집 속도는 새 기획값이다. 기존 애니메이션 타격 프레임과 어긋나면 클립 이벤트에 맞춰 타이밍을 조정하고 완료 시간도 다시 측정한다. 화면 비주얼 크기·등짐 회전·카드 오프셋은 사용자가 조정한 값을 그대로 기준으로 삼는다.

### 4.3 건설 가격과 기준 수급표

시작 목재 0개. S1부터 S4까지 순서대로 활성화한다.

| 단계 | 비용 | 기준 플레이어 공급 | 기준 일꾼 공급 | 누적 비용 | 해금 |
|---|---:|---:|---:|---:|---|
| S1 기지 창고 | 6 | 6 | 0 | 6 | 창고 저장 기능 |
| S2 벌목 오두막 | 12 | 12 | 0 | 18 | 일꾼 1명 |
| S3 진입로 확장 | 18 | 12 | 6 | 36 | 가공소 부지·두 번째 작업 구역 |
| S4 가공소 | 24 | 6 | 18 | 60 | 일꾼 2명, 각 운반량 12 |
| **합계** | **60** | **36** | **24** | **60** | 4단계 완료 |

기준 플레이어 벌목은 6그루 상당이다. 일꾼은 4회 납품한다. S2가 18초에 완성됐다고 가정하면 첫 일꾼의 납품은 24·30·36·42초에 6개씩, 총 24개다. 따라서 수급상 S4는 42초 이후 완료 가능하고 납품·완성·보상 관찰을 포함하면 약 50초가 된다. **이는 수급 계산이며 실제 길찾기·입력 시간을 검증한 플레이 시뮬레이션은 아니다.**

이 배분을 강제하지 않는다. 직접 더 캐면 더 빨리 완성하며, 일꾼 자원을 기다려도 진행된다. 일꾼 오류 시에도 총 10그루 상당을 직접 캐면 60개를 마련할 수 있다. 다만 이는 경제적 막힘 방지이고, 일꾼 오류가 있는 빌드의 출고 허용 조건은 아니다.

### 4.4 일꾼 생산의 정확한 정의

일꾼별 고정 작업 구역 하나와 창고를 연결한다. 전체 지도 길찾기·동적 장애물 회피는 필요하지 않다. 6초 주기의 초기 시간 예산은 이동 1.5초 + 작업 1.5초 + 복귀 1.5초 + 납품 0.6초 + 여유 0.9초다. 업그레이드 후 납품 1.2초이므로 여유는 0.3초다.

작업 완료 시 목재를 일꾼 등짐에 생성하고, 창고 도착·납품 때만 창고 잔고가 늘어난다. 재화 생성 타이머와 애니메이션이 별개로 중복 보상하지 않는다. 일꾼 전용 작업 자원은 노선에 예약하여 플레이어가 먼저 캐는 경쟁을 없앤다. 두 일꾼의 경로도 분리한다.

S4가 완성되면 기존 운반 중 목재는 그대로 유지한다. 증가된 생산량은 **다음 작업 완료분부터** 적용한다. 새 일꾼은 등장 연출 후 자기 작업을 시작한다. ‘4배’는 다음 정상 주기들의 합계 처리량이며 즉시 잔고 4배가 아니다.

### 4.5 막힘과 중복 결제 방지

- 등짐에 6개가 들어갈 자리가 없으면 다음 나무 벌목을 시작하지 않고 납품 방향을 강조한다. 이미 시작한 벌목의 보상 자리 6개는 예약한다.
- 땅 드롭은 최대 24개. 자리가 없으면 새 벌목을 기다리게 하고 기존 자원을 유지한다. 정상 동선에서 자주 발생하면 수집 반경·드롭 수명 정책을 재조정한다.
- 물류 노드 하나는 획득·운반·입고 중 한 소유자만 가진다. 같은 목재를 등짐·창고에 동시에 넣지 않는다.
- 납품 1개마다 `남은 가격`, `등짐/창고 잔고`를 함께 확인하고 한 번만 감소시킨다. 가격을 초과하는 자원은 보관한다.
- 여러 자원 이벤트가 같은 프레임에 와도 건물 보상·일꾼 생성·단계 해금은 각각 한 번이다.
- 중간에 납품 구역을 나가면 진행량은 유지하고, 재진입 시 남은 비용만 지불한다.
- 창고가 120개로 차면 일꾼은 납품 가능한 수량만 내리고 남은 짐을 보유한 채 대기한다. 자원 삭제·무한 생성·노드 누적 금지.
- 튜토리얼에는 실패·사망·기지 파괴·유료 선택이 없다. 무입력 시 안내만 재노출한다.
- 앱 숨김 시 생산과 이동을 멈춘다. 복귀 시 누적 시간만큼 한꺼번에 지급하지 않는다.

## 5. 필요한 자원 및 에셋

### 5.1 제작 범위

사용자에게 확인된 준비물은 메인 캐릭터, 목재, 건물 에셋이다. 아래 ‘재사용’은 **존재·적합성을 직접 검수했다는 뜻이 아닌 우선 검토 대상**이다. 구현 시작 시 Claude가 필요한 참조와 동작만 확인한다.

| 에셋 | 필요한 고유 종류 / 화면 상한 | 제작·재사용 방법 | 초기 납품 규격 / 주의 |
|---|---|---|---|
| 플레이어·일꾼 | 캐릭터 원형 1종 / 동시 3명 | 기존 캐릭터·애니메이션 공유. 일꾼은 작은 색 표식으로 구분 | 새 리깅 없음. 대기·이동·벌목 클립만 필수 |
| 통나무 | 1종 / 아래 풀 상한 | 기존 wood 재사용 | 플레이어가 맞춘 크기·회전 기준 유지. 드롭 루트 스케일 애니메이션 주의 |
| 플레이어용 나무 | 1종 / 초기 6그루 | 기존 나무 우선, 크기·회전으로 변주 | 줄기 피벗에 기울기·스케일 연출. 새 파괴 메시 없음 |
| 일꾼 작업용 나무 | 같은 원형 / 2그루 | 일꾼별 예약 작업 지점 | 일반 6그루와 자원 소유권 분리. 총 상호작용 나무 8그루 |
| 기지 창고 | 1종 | 기존 건물 활용, 필요 시 고정 시점 카드 | 건설 전은 실루엣/밑판, 완료 후 완성 이미지 |
| 벌목 오두막 | 1종 | 기존 건물 활용, 입구만 별도 간단한 판/메시 | 일꾼은 입구 앞에서 등장. 새 문 리깅 불필요 |
| 가공소 | 1종 | 기존 건물 활용, 간판·색 포인트로 역할 구분 | 선택적으로 톱니 1개 회전. 별도 판자 생산 연출 없음 |
| 진입로·경계 | 길 타일 1종, 경계 조각 1종 / 경계 최대 6개 | 단순 박스·판과 공용 텍스처 | 경계 내려가기 + 길 활성화. 물·다리 물리 불필요 |
| 다음 구역 미리보기 | 이미지 1장 | 기존 건물 실루엣 재조합 | 추가 3D 건물·상호작용 시스템 미포함 |
| 바닥·장식 | 바닥 1장, 장식 최대 2종 | 기존 바닥과 카드 활용 | 단순 색 바탕 우선, 화면 밖 장식 최소화 |
| 캐릭터 그림자 | 텍스처 1장 / 동시 3장 | 기존 가짜 그림자 공유 | 캐릭터별 동적 그림자 패스 없음 |
| UI | 목재·일꾼·잠금·화살표·손·체크·버튼 등 7요소 | 아이콘 제작 후 아틀라스 1장 | 512×512 출발, 숫자/간단 문자만 별도 글리프 |
| 효과 | 공용 먼지/반짝임 아틀라스 1장 | 2D 스프라이트 또는 작은 파티클 | 256×256, 스켈레톤 이펙트 없음 |
| 효과음 | 벌목·흡수·납품·완성·고용·확장 6종 | 짧은 모노 음원, 같은 음원의 피치 변화 | 22.05~44.1kHz 후보를 실기기 비교, 총 패키지 예산 우선 |
| BGM / 영상 | 0개 | v1 미사용 | 무음 상태에서도 모든 목표가 읽혀야 함 |

건물 3종을 카드로 새 제작해야 한다면 **건물당 바닥 이미지 1장 + 기운 면 이미지 1장**, 총 6장이 필요하다. 두 이미지는 동일 캔버스 크기·동일 접점 기준으로 납품한다. 512×512 또는 512×256 등 실제 표시 크기에 맞춰 시작하고, 불필요한 투명 여백을 줄인다. 쌍의 크기와 접점을 함께 유지하며, 한 이미지씩 제각각 잘라내지 않는다.

`TextureCard`의 세로 보정·법선 오프셋·개체별 텍스처 지정은 기존 기능을 사용한다. 가공소처럼 움직이는 작은 부품만 별도 메시로 둔다. 배치마다 고유한 대형 텍스처를 추가하는 방식은 피한다.

### 5.2 연출과 색감 기준

- 플레이어·활성 목표·목재가 배경보다 먼저 읽혀야 한다. 목표 구역은 색뿐 아니라 목재 아이콘과 숫자로 구별한다.
- 등짐 12개는 캐릭터보다 높게 보일 수 있으나 목표 가격·CTA를 가리지 않게 한다. 기존 사용자 배율을 바꾸기 전 실제 화면으로 검수한다.
- 건설 연출은 준비된 완성 노드 활성화 + 0.6초 팝 연출 + 작은 먼지로 구성한다. 단계별 대형 텍스처 시퀀스는 만들지 않는다.
- 카드 unlit은 조명의 영향과 출력 톤매핑을 구분한다. 두 이미지 쌍과 기존 건물 사이 밝기·채도·그림자 방향을 비교한다.
- 몸체 standard 머티리얼은 유지하는 전제다. 용량 절감만을 이유로 toon이나 unlit으로 일괄 변경하지 않는다.

## 6. Claude Code에게 전달할 기능 구현

### 6.1 문서상 재사용 후보

아래 이름은 프로젝트 문서에서 확인했다. 현재 코드의 API·씬 연결 상태는 직접 검사하지 않았으므로 **그대로 연결하면 된다고 확정하지 않는다.**

| 필요한 동작 | 문서상 후보 | Claude가 우선 확인할 점 |
|---|---|---|
| 이동·자동 벌목 | `Player`, `Choppable` | 타격 이벤트·보상 수량·거리 판정 노출 여부 |
| 드롭·수집·등짐 | `CoinPool`, `Coin`, `CoinStack` | 이름은 Coin이어도 wood를 쓰는 설정 유지. 재화 중복·상한 처리 |
| 납품·순서 해금 | `Socket`, `SocketManager` | 기존 추종자·러쉬 보상과 분리 가능한 이벤트/설정인지 |
| 일꾼 운반 | `CoinCourierManager` | 노선 데이터와 실제 채집 포함 여부. 단순 운반이면 생산 작업만 추가 |
| 건물 접근·경계 | `BuildingTrigger`, `DoorAutoOpen`, `VirtualWall` | 문서에는 존재만 확인된 부분이므로 기능 동등성부터 조사 |
| 길 안내·월드 UI | `GuideCompass`, `WorldUIAnchor`, `UIAutoFit` | 현재 목표 추적, 세로/가로에서 가림·입력 문제 없는지 |

## 7. 최적화 방안과 구현 순서

### 7.1 5MB 출고 기준

AppLovin 공식 안내는 **5MB 이하의 단일 HTML, 내장 리소스, 외부 네트워크 요청 금지, 양방향 화면 대응**을 요구한다. MRAID v2 준비 상태 확인, `mraid.open()` 클릭 처리, 첫 조작 전 음소거, 숨김 시 음소거, WebGL 초기화 실패·컨텍스트 손실 UI 폴백도 요구한다. [AppLovin 공식 규격](https://support.applovin.com/en/growth/promoting-your-apps/welcome-to-applovin/creative-specs-and-guidelines)

이 프로젝트는 단위를 보수적으로 잡아 최종 HTML **5,000,000바이트 미만**, 내부 목표 **4,500,000바이트 이하**로 정한다. HTML 원문 파일의 디스크 크기를 측정하며 zip 압축 크기·소스 에셋 합·HTTP gzip 전송량으로 대체하지 않는다. 원본 바이너리는 base64 인코딩 시 대략 4/3으로 늘 수 있지만, 현재 어댑터의 압축 순서에 따라 달라지므로 최종 파일을 측정한다.

| 항목 | 최종 HTML 기여분 계획 예산 |
|---|---:|
| 엔진·로더·광고 어댑터 | 2,750,000 B |
| 메시·스켈레톤·필수 클립 | 450,000 B |
| 건물·나무·지면 텍스처 | 600,000 B |
| 캐릭터 텍스처 | 150,000 B |
| UI·아이콘·제한된 글리프 | 180,000 B |
| 효과음 | 70,000 B |
| 씬·게임 스크립트·머티리얼·효과 | 100,000 B |
| 내부 변경 여유 | 200,000 B |
| **내부 목표 합계** | **4,500,000 B** |

**측정 결과가 아닌 예산 배분이다.** 문서에 있는 엔진 2.68MB도 과거 측정으로, 이번 빌드의 확정값은 아니다. 전체 압축은 상호 영향을 받아 항목별 기여분을 정확히 분리하기 어려우므로, 포함 목록·해제 크기·동일 조건 증분 빌드를 함께 기록한다. 항목별 예산을 만족해도 최종 HTML 검사에 실패하면 출고하지 않는다.

### 7.2 용량을 줄이는 개발 순서

1. **기준 빌드부터**: 씬3만 포함한 release HTML로 엔진·어댑터·필수 캐릭터 비용을 측정한다. 기능 전체를 만든 뒤 처음 용량을 재지 않는다.
2. **참조 범위 축소**: 씬1·2, 사용 안 하는 resources/번들, 중복 모델·미사용 애니메이션이 출고 파일에 들어가는지 디코딩해 확인한다. 원본 프로젝트 자산 삭제 대신 출고 포함 범위를 줄인다.
3. **애니메이션 선택**: 대기·이동·벌목부터 포함한다. 클립 제거 시 그래프와 다른 씬의 참조를 보존한다. 캐릭터가 여러 명이어도 원본 바이너리를 중복 임베드하지 않는다.
4. **메시 정리**: 불필요한 UV·컬러·스킨 속성은 실제 셰이더·스키닝 사용 여부 확인 후 제거한다. 본 일괄 삭제로 기존 Bone_Stick 처리·클립을 깨뜨리지 않는다.
5. **이미지 정리**: 실제 화면 픽셀 크기로 줄이고 알파 여백을 줄인다. 불투명은 JPEG 후보, 투명은 PNG/WebP 후보를 실제 WebView에서 비교한다. 알파 가장자리·카드 짝의 접점·색감은 검수한다.
6. **UI·문자**: 숫자/짧은 문구 중심. 배포 언어별 필요한 글리프만 포함하거나 시스템 폰트를 쓴다. 전체 한글 폰트 파일을 무심코 추가하지 않는다.
7. **기능 제거**: 프로젝트 단위 Feature Cropping이 씬1·2도 건드릴 수 있으므로 출고 프로필/설정 복원과 회귀 검증을 전제로 적용한다. 미사용 물리·Spine 등은 의존성 확인 후 제외. [Cocos Project Settings](https://docs.cocos.com/creator/3.8/manual/en/editor/project/)
8. **순차 축소**: 초과하면 장식·다음 구역 이미지·추가 효과음부터 축소한다. 이후 건물 텍스처와 필수 메시를 검토한다. 벌목→건설→일꾼 납품이라는 핵심 피드백을 먼저 없애지 않는다.

압축 포맷 도입으로 필요한 디코더가 더 커질 수 있다. Draco/KTX 등의 도입은 이름만 보고 결정하지 말고 전체 HTML·초기화 시간·WebView 지원을 함께 비교한다. GPU 압축과 파일 용량 절감도 별도 지표다.

### 7.4 실제 구현할 최적화

- **풀링과 준비 시점**: 드롭·등짐·날아가는 자원·효과를 미리 준비하고 재사용한다. 큰 프리팹 생성·머티리얼 생성·셰이더 첫 사용이 S2 고용/S4 완성과 겹치지 않게 준비한다. 준비를 여러 프레임으로 나눌 경우도 시작 준비 시간 목표를 확인한다.
- **공용 메시·머티리얼**: 같은 통나무와 불투명 나무는 공유하고 인스턴싱 효과를 실측한다. 머티리얼이 같은 이름이라고 자동으로 합쳐지지 않는다. 개별 텍스처·MaterialInstance를 쓰는 2D 카드는 자동 배칭을 가정하지 않는다.
- **두 면 카드의 비용**: `plane2x2_ground`는 서브메시/머티리얼이 둘이므로 통상 면별 드로우가 생긴다. 건물 3개면 약 6드로우를 먼저 예산에 넣고 실제 패스 수를 확인한다. 독립 이미지 기능은 유지하고 꼭 필요한 건물에만 쓴다.
- **투명 오버드로**: 큰 투명 면을 겹치지 않게 배치한다. 반투명 접지 그림자는 유지하되 완전 투명 여백을 줄인다. 컷아웃은 가장자리와 그림자가 허용하는 일부 장식에서만 검토한다. 알파 테스트를 켰다고 모든 투명 비용이 사라지는 것은 아니다.
- **Cocos 배칭 한계**: 같은 메시·머티리얼이 기본 조건이며, 투명 인스턴스 정렬과 비균등 스케일 법선에 제약이 있다. 실시간 스켈레탈 애니메이션은 해당 동적 배칭 대상이 아니므로 캐릭터 3명을 자동 1드로우로 계산하지 않는다. Bone_Stick 처리 때문에 baked로 일괄 전환하지 않는다. [Cocos MeshRenderer](https://docs.cocos.com/creator/3.8/manual/en/engine/renderable/model-component.html), [Instanced Attributes](https://docs.cocos.com/creator/3.8/manual/en/shader/instanced-attributes.html)
- **판정 비용**: 현재 활성 건설 구역 1개만 검사한다. 거리·AABB 판정과 기존 VirtualWall을 쓰고 새 물리 엔진·NavMesh를 추가하지 않는다. 일꾼은 고정 경유점, 목표 탐색은 5~10Hz 후보, 이동 보간은 프레임마다 수행한다.
- **재화와 화면 분리**: 창고 120개를 120모델로 그리지 않는다. 논리 잔고는 정확하게 유지하고 화면은 최대 8개. 비행 연출 풀이 가득 차면 연출만 생략하고 지불·잔고는 정확히 처리한다.
- **UI와 할당**: 숫자는 값 변경 시만 갱신하고 매 프레임 문자열·배열·벡터를 생성하지 않는다. 정적 HUD는 리사이즈 시 레이아웃 갱신. 월드 UI는 현재 목표만 표시한다.
- **품질 단계**: 해상도→부수 효과→장식 순서로 낮춘다. 등짐·납품·일꾼 첫 동작은 유지한다. 품질 변경마다 프레임을 측정하고 실패 원인이 GPU인지 스크립트인지 구분한다.
- **메모리**: 1024×1024 RGBA 텍스처 한 장은 압축 해제 시 약 4MiB이며 밉맵·복사본은 별도다. GPU 텍스처 메모리 32MiB 이내를 초기 목표로 삼고 전체 프로세스 메모리 보장으로 혼동하지 않는다.

### 7.5 출고 검증

1. 낮은 등급 Android 1대, 중급 Android 1대, iPhone 1대의 **실제 WebView/광고 프리뷰**에서 각각 3회 확인한다. 기종·OS·WebView 버전·품질 등급을 기록한다. PC 프리뷰만으로 통과하지 않는다.
2. 첫 준비, 첫 벌목, 첫 일꾼 생성, 가공소 완성, 최대 등짐/드롭, 엔드카드 장면의 프레임 시간을 따로 기록한다.
3. 세로→가로 회전, 숨김→복귀, 오디오 상태, CTA, WebGL 실패/컨텍스트 손실 폴백을 확인한다.
4. 빠른 경로, 기준 경로, 천천히 대기하는 경로, 수동만으로 60개 모으는 경로를 테스트한다. 재화 보존식은 항상 `생성 누계 = 지불 누계 + 등짐 + 일꾼짐 + 땅 + 창고 + 소유권이 남은 이동 중 재화`다. 시각 효과 사본은 재화로 세지 않는다.
5. 반복 리셋 3회와 엔드카드 배경 3분 실행 후 노드·풀·이벤트 리스너가 계속 증가하지 않아야 한다.
6. 최종 HTML 바이트 수와 실제 내장 데이터 목록을 확인한다. 배포본에 디버그 HUD·source map·외부 에셋 요청이 없는지 검사한다. MRAID 호스트 연결은 기존 어댑터와 공식 프리뷰에서 검증한다.

## 8. 검증할 기획 지표와 변형 실험

공개 사례의 수치를 우리 KPI로 복사하지 않는다. 첫 빌드는 내부 관찰로 이해도·진도·끊김을 확인하고, 광고 집행 후 비교 지표를 잡는다.

| 관찰 지표 | 첫 내부 목표 / 정의 | 미달 시 먼저 바꿀 것 |
|---|---|---|
| 첫 벌목 도달 | 첫 입력 후 3초 내, 새 테스트 인원 5명 중 4명 목표 | 시작 거리·가이드·자동 타격 범위 |
| 첫 건설 도달 | 기준 7초 내 목표 | 납품 동선·구역 가독성 |
| 자동화 이해 | 테스트 후 ‘일꾼이 무엇을 해줬는가’ 설명 가능 | 첫 납품 위치·카메라·저장량 피드백 |
| 첫 고용 | 첫 입력 후 18초 전후 목표 | S2 비용·나무 배치. 생산 속도부터 몰래 올리지 않음 |
| 성공 도달 시간 | 내부 기준 경로 45~60초 목표 | 이동·대기·투입 시간을 구분해 조정 |
| 단계 전환율 | 각 단계 도달자 / 직전 단계 도달자 | 이탈이 큰 구간 하나씩 수정 |
| 광고 성과 | IPM=설치/노출×1000, CTR=클릭/노출, 클릭→설치 및 가능한 설치 후 품질 | CTR만 높아지는 변형을 승자로 단정하지 않음 |

계측 이벤트 제안: `first_input`, `first_harvest`, `stage_paid(S1..S4)`, `worker_first_deposit`, `automation_upgraded`, `success_reached`, `cta_shown(reason)`, `cta_clicked`, `quality_changed`.

로컬 개발 계측은 메모리·디버그 로그로 한다. 배포 이벤트는 네트워크/어댑터가 지원하고 허용하는 방식만 연결한다. 임의의 분석 SDK나 외부 수집 URL을 추가하지 않는다. 광고 플랫폼에서 얻지 못하는 단계별 지표는 내부 테스트 자료라고 명시한다.

첫 비교는 **첫 화면 한 요소만** 바꾼다.

- A안: 목재 0개·나무 바로 앞 시작. ‘내 손으로 처음부터’의 성취감.
- B안: 목재 4개를 등에 보유·0/6 창고 앞 시작. 즉시 부분 납품 후 나무로 이동하는 완성 욕구. 이 경우 시작 재화 4개를 별도 발행으로 기록하고 필요한 채집량을 다시 계산한다.

v1 기본안은 A다. B는 코드와 공용 에셋은 같고 설정만 다른 별도 빌드로 비교한다. 승자 선택은 동등한 타기팅·기간·충분한 표본에서 하며, 작은 내부 테스트를 설치율 증거로 제시하지 않는다.

## 9. 제작 순서와 이번 산출물의 범위

| 순서 | 담당 | 산출물 / 다음 단계 조건 |
|---|---|---|
| 1 | 사용자 + Codex | 후킹·4단계 흐름·목재 1종 방향 검토 |
| 2 | Claude | 현재 기능 재사용표, 캐릭터 상태 확인, 기준 HTML 크기 |
| 3 | Claude | 기존/임시 에셋으로 S1→S4 경제와 일꾼 납품 완주 |
