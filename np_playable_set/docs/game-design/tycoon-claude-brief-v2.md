# Claude Code 전달용 구현 브리프 v2 — 판매·회수·투자 루프

작성: 2026-09-16. **v1 구현 브리프를 대체한다.** 문서 작성만 수행했으며 개발 착수를 외부에 전달한 것은 아니다.

## 반드시 지킬 기획 전제

플레이어는 자원을 획득하고 판매하여 코인을 얻고, 코인을 소켓에 넣어 기지를 발전시킨다. 발전 결과는 화면과 실제 효율에 나타나야 하며, 다음 더 큰 수급·판매 사이클을 완료한 뒤 종료한다. **목재를 바로 건설비로 쓰는 v1 구조를 구현하지 않는다.**

사용자가 말하는 소켓은 요구 자원/재화를 받아 가공·판매·건설·유닛 생산 등의 결과를 내는 영역이다. 기본안에는 반복 판매 소켓과 1회 업그레이드 소켓이 있다. 가공 소켓은 후속 변형이며 기본안에서는 만들지 않는다.

기준 문서: `tycoon-playable-v2.md`. 숫자 원본: `tycoon-balance-v2.json`(엔진 자동 임포트 파일이 아님). 기존 `CLAUDE.md`와 `docs/cocos-notes`의 공유 코드·에셋·인스펙터 값 보호 규칙도 유지한다.

## 경제와 성장

| 항목 | 구현 기준 |

## 구현 순서와 수락 조건

### P0. 현재 기능 확인과 자원 구분

- 이번 기획 작업에서는 에셋/코드를 직접 확인하지 않았다. Player, Choppable, CoinPool, CoinStack, Socket, SocketManager, CoinCourierManager, 가이드·CTA는 문서상 재사용 후보다.
- 문서에 남은 FBX/캐릭터 장애가 현재 해결됐는지 먼저 확인한다. 구버전 경로·러쉬 디펜스 설명을 이번 대상과 혼동하지 않는다.
- 기존 Coin 클래스가 목재를 표시하더라도 resourceId=wood와 currencyId=coin의 소유권·장부를 분리한다. 기존 wood 비주얼을 코인으로 되돌리거나 필드 이름을 일괄 변경하지 않는다.
- 공유 코드/씬1·2 기본 동작을 보존하면서 재사용 가능한 자원/소켓 설정으로 확장한다.
- 씬3 단독 release 기준 HTML 크기와 기능 재사용/추가 필요 목록을 보고한다.

### P1. 판매·반환·회수의 완결된 거래

판매 목재를 예약→비행→판매대 도착→목재 소비/매출 확정→지급함 대기→코인 회수 예약→지갑 입금 순서로 처리한다. 실제 구현 상태명은 자유지만 각 자원의 소유자는 항상 하나다.

- 목재는0.10초에1개 투입. 지급함300코인 한도는 접수 시 매출액을 예약해서 보장한다.
- 코인 묶음은 최대5코인. 회수 출발 간격0.08초, 판매 후0.15초부터 회수 가능, 비행0.25초 후보.
- 판매/회수 영역은 겹쳐 플레이어가 판매 중 코인도 받는다. 투자 영역은 떨어뜨려 원치 않는 연쇄 지불을 막는다.
- 일꾼은 별도 납품 슬롯을 사용하고 매출은 같은 지급함으로 들어간다. 지갑에 바로 입금하지 않는다.
- 지급함이 차면 새 판매만 대기하고 현재 짐과 접수 거래를 보존한다. 자원을 삭제하거나 코인 노드를 계속 생성하지 않는다.
- 소켓 이탈/비행 중 숨김/복귀/애니메이션 취소에 대한 거래 완료·대기 정책을 명시한다. 모델 active 여부로 지급 여부를 결정하지 않는다.
- 첫 수락 기준: 목재6개 판매 후 목재0, 지갑30, 지급함0이며 나무 투입과 코인 회수가 화면에 보인다.

### P2. 투자·효율 향상·재판매

- 현재 투자 단계 하나만 활성화. 0.08초마다 최대5코인 납입하고 잔여 가격·지갑 금액으로 제한한다.
- 부분 납입은 유지, 초과 금액은 지갑에 보존. 완료 이벤트와 설비/일꾼 보상은 한 번만 발생.
- U1은 다음 새 나무부터 채집력3. 진행 중인 벌목에는 기존 스냅샷을 유지한다.
- 타격 준비0.20초 + 간격0.40초 + 회복0.20초: 3타1.2초→1타0.4초. 실제 클립 접촉 프레임과 맞춰 검수한다. 수익률3배로 표시하지 않는다.
- U1 뒤12목재→60코인을 직접 판매·회수한 다음 U2로 연결한다.
- 안내 우선순위는 현재 경제 상태로 정한다: 목재 부족→나무, 보관 포화/판매할 목재→판매대, 회수 가능 대금→지급함, 충분한 지갑/진행 중 납입→현재 투자. 너무 잦은 목표 전환은 억제한다.

### P3. 자동화와 확장

- 일꾼1명8초/6목재. 이동1.5+작업3+복귀1.5+판매0.6+여유1.4초 예산. 실제 동선으로 검증한다.
- 작업 완료 시 목재 보유, 판매대 납품 완료 시 지급함 코인 생성. 단순 타이머 입금과 외형 애니메이션을 따로 실행하지 않는다.
- 일꾼별 작업 지점/경유점/판매 슬롯을 예약한다. 플레이어가 작업 자원을 빼앗지 않게 한다. NavMesh나 새 물리 엔진 불필요.
- U3는 외형 공개·통행 해제·일꾼2·플레이어 보관18을 같은 성장 이벤트로 연결한다.
- 이미 생성된 짐과 진행 중 거래는 보존한다. 모델 크기·회전은 사용자 튜닝을 기준으로 한다.

### P4. 성장 사이클 완료 판정

U3 이후 epoch를 부여해 자원 획득 시점, 판매 시점, 회수 시점과 actor를 추적한다.

- 플레이어 조건: U3 이후에 획득한 목재12개 이상이 판매되고 대금까지 회수됨.
- 일꾼 조건: 각 일꾼이 U3 이후 판매한 적이 있고 그 대금이 회수됨. U3 전에 작업한 짐이라도 U3 이후 실제 판매라면 일꾼 조건에는 인정한다.
- 금액 조건: U3 이후 판매분 중 회수 완료된 코인120 이상. 이전 지급함 잔액은 제외한다.
- 지갑 총액이나 소켓 방문 횟수만으로 성공 판정하지 않는다. 거래 receipt ID로 중복 누적 방지.
- 세 조건을 만족하면 정산 숫자와 기지 전경을2초 보여주고 성공 패널. 정산 표시는 이미 받은 돈의 집계이며 다시 지급하지 않는다.
- 첫 입력 이후 활성75초 미완료 시 보조 CTA만 노출. 정상 성공으로 표시하거나 강제 리다이렉트하지 않는다.

### P5. 풀·출고·실기기 검증

- 목재 최대62노드: 땅24+플레이어18+일꾼12+판매 비행8.
- 코인 최대24노드: 지급함8+회수8+투자8. 5코인 토큰을 반복 재사용해 연속 투입을 유지한다.
- 스켈레탈3명, 상인 정적1명, 나무8그루, 파티클24개 상한. 캐릭터는 가짜 그림자.
- 정상 경로에서 소켓 연출이 생략되지 않도록 준비한다. 연출 풀이 모자라도 장부 자원을 버리지 않는다.
- 같은 모델/머티리얼 공유·가능한 인스턴싱을 검증. 개별 카드 머티리얼·투명 정렬·실시간 스켈레탈 캐릭터를 자동 배칭으로 계산하지 않는다.
- 최초 판매 전 리소스를 준비하되 파일 전달 후 준비 시간도 측정한다. 판매마다 생성/파괴·텍스처 로드·셰이더 컴파일이 발생하지 않게 한다.
- 최종 HTML 내부 목표4,500,000 B 이하, 출고5,000,000 B 미만. 디코딩한 실제 내장 데이터와 최종 파일 크기를 검사한다.
- 첫 판매·투자 완성·일꾼 동시 납품·최종 정산의 p95/p99와100ms 이상 정지 측정. 드로우콜 일반60/피크80 경고선, 중급60fps/낮은 등급30fps 목표.
- 실제 Android2등급+iPhone에서 세로/가로·음소거·숨김/복귀·CTA·WebGL 폴백 확인. PC 프리뷰만으로 통과 선언하지 않는다.

## 반드시 검증할 경제 사례

1. 판매대에 넣던 중 이탈: 접수분만 판매, 나머지 목재 보유, 미회수 코인 유지.
2. 코인30 중15만 투자 후 이탈: 재진입 시 나머지15만 지불.
3. 플레이어/일꾼 동시 판매: 정확한 판매자·매출·지급함 예약, 중복 거래 없음.
4. 지급함 잔액295에 두 건 동시 접수: 한 목재 판매만 추가 예약 가능, 나머지는 대기.
5. 풀 포화/숨김/복귀: 목재·코인 각각 보존, 지갑 중복 입금 없음.
6. U3 이전 코인120을 남겨 둠: 그것만 회수해서 성공할 수 없음.
7. U3 전에 채집해 둔 플레이어 목재12를 이후 판매: 매출은 정상이나 ‘U3 이후 플레이어 채집’ 조건에는 불충족.
8. 성공 집계를 여러 번 갱신: 정산액 재지급·CTA 반복 생성 없음.
9. 판매대에서 그대로 서 있음: 코인 회수는 되지만 옆 투자 소켓으로 원치 않는 지불은 안 됨.
10. 반복 리셋3회와 종료 후3분 실행: 노드/풀/리스너가 계속 늘지 않음.
