- **지위**: 기획 확정. 여기 적힌 것은 추론이 아니라 **사용자가 직접 말한 것**이다.

> 명세 변경이 아니라 **위반**이다. 명세와 다르게 구현할 이유가 생기면 고치지 말고 물어본다.

## 2. 트리거 표 — 구현의 단일 기준

`TriggerId`는 **1~16 = 소켓 충족 신호**, **100번대 = 소켓과 무관한 진행(플로우) 신호**로 구간을 나눠 쓴다.

| TriggerId | 발화 조건 | 발화하면 일어나는 일 |
|---|---|---|
| `Trigger1` | WorkerLodge 건설 소켓 완료 | WorkerLodge 등장 · 생산 소켓 A1 등장 · Warehouse 건설 소켓 등장 |
| `Trigger2` | Warehouse 건설 소켓 완료 | Warehouse 등장 · 나무 적재 소켓 B1 등장 · **일꾼 채집 활성화** · 광산 건설 소켓 등장 |
| `Trigger3` | 광산 건설 소켓 완료 | ironMine **active 전환** · 생산 소켓 A2 등장 · 철 적재 소켓 B2 등장 |
| `Trigger4` | Blacksmith 건설 소켓 완료 | Blacksmith 건설 · **SwordShop · ground_dirt 2종 · 울타리 동시 건설** · **사라지는 나무 제거** |
| `Trigger5` | 레일 1 소켓 완료 (코인 요구) | 레일: Warehouse → Blacksmith 자동 운반 |
| `Trigger6` | 레일 2 소켓 완료 (코인 요구) | 레일: Blacksmith → SwordShop 자동 운반 |
| `FirstIron` = 101 | 플레이어가 **철을 처음 수집** | Blacksmith 건설 소켓 **개방** |
| `FirstCoin` = 102 | 플레이어가 **코인을 처음 수집** | 레일 소켓 2개 **개방** |
| `GameClear` = 103 | `Trigger5` **와** `Trigger6`이 모두 발화 | 게임 종료 연출 / CTA |

> 🔴 **101~103은 소켓이 채워서 나오는 신호가 아니다.** 각각 "자원을 처음 먹었다", "두 소켓이 다 찼다"는
> 게임 진행 사실에서 나온다. 그래서 `SocketManager.sockets`에 넣을 수 없고 별도 발화 지점이 필요하다.

## 3. 소켓은 3종류다 — 섞지 말 것

| 종류 | 하는 일 | 쓰이는 곳 | 구현 |
|---|---|---|---|
| **건설 소켓** | 요구 자원을 채우면 **트리거를 발화**하고 사라진다 | WorkerLodge · Warehouse · ironMine · Blacksmith · 레일 D1·D2 | 기존 `Socket` |
| **생산 소켓** | **플레이어가 서 있으면** 게이지가 차올라 일꾼 1마리 배출. 서 있는 한 **무한 반복** | WorkerLodge의 A1(나무) · A2(철) | 신규 `SpawnerSocket` |
| **적재 소켓** | 자원이 **쌓여서 보관**된다. 트리거를 발화하지 않는다 | 창고 앞 나무 B1·철 B2 / 상점의 칼 / 상점 옆 코인 | 기존 `CoinGroundStack` (= 옛 coin_ground 역할) |

**적재 소켓의 필수 요건**: 소켓마다 **화면에 보여줄 최대 개수**를 설정할 수 있어야 한다.
실제 보유량은 **데이터로 계속 센다** — 표시 개수는 상한일 뿐 실제 개수와 다르다.

**건설 소켓의 요구 자원**

| 소켓 | 요구 |
|---|---|
| WorkerLodge | 나무 |
| Warehouse | 나무 |
| ironMine | 나무 |
| **Blacksmith** | **나무 + 철 동시** ← 이제까지와 다른 유일한 것 |
| 레일 D1 | 코인 |
| 레일 D2 | 코인 |

## 4. 일꾼

- **2종** — 나무 일꾼 / 철 일꾼. **각각 최대 10마리** (합계 20마리가 상한이 아니라, 종류마다 10).
- 생산: 플레이어가 생산 소켓에 **서 있으면** 게이지가 차고 1마리 배출. 계속 서 있으면 계속 나온다.
  **상한 10마리에 도달하면 더 나오지 않는다.**
- 이동: **최소 거리 경로를 계산해서** 움직인다.
- **나무 일꾼**: 플레이어처럼 **나무에 찾아가서 chop** 한다.
- **철 일꾼**: 광산의 **입구 지점**(위치는 **사용자가 직접 지정**)에 도착하면 **사라진다**(광산에 들어간 상태)
  → **일정 시간**(인스펙터에서 **조정 가능해야 함**)이 지나면 → **wagon 상태로 나와서** 창고로 간다.
- **자원 보유**: 일꾼은 자원을 **등에 싣지 않는다. 흡수만 한다** — 몇 개 챙겼는지는 **데이터로만 센다.**
- **운반**: 보유량이 **10개**가 되면 **wagon 애니메이션**을 하며 Warehouse로 옮겨 적재한다.
- 🔴 **Warehouse 건설 전에는 일꾼이 자원을 챙기지 못한다.** 벤 나무는 흡수되지 않고 **바닥에 떨어져**
  플레이어가 줍는다. **Warehouse 건설 완료와 동시에** 챙기기 시작한다.

## 6. 손님

- 프리팹을 **새로 제작해야 한다.** 플레이어 캐릭터를 쓰되 **`green_bob`을 사용한다.**
- 등장: 칼이 상점에 쌓이면 **`ground_sub` 공간에서 줄지어** 온다.
- 행동: 상점 앞에 **줄을 선다** → **칼을 3개씩** 사 간다 → **코인을 지불**한다.
- 지불: SwordShop **옆의 코인 적재 소켓**에 코인이 쌓인다 → **플레이어가 직접 수집**한다.
  (손님이 플레이어에게 직접 주는 것이 아니다.)

---

## 7. 대장간

- **나무 1 + 철 1 = 칼 1.**
- 플레이어가 창고의 나무·철을 **등에 싣고** 대장간에 넣는다.
- 대장간이 칼을 뱉으면 **플레이어가 수집**한다.
- 플레이어가 그 칼을 SwordShop에 **가져다 놓아 쌓는다** (일꾼이 창고 앞에 쌓는 것과 같은 방식).

---

## 8. 레일

- 개방: **플레이어가 코인을 처음 수집**하는 순간 소켓 2개가 각각 생긴다.
- **소켓 위치는 사용자가 직접 잡는다.**
- 두 소켓 모두 **코인을 요구**한다.
- 레일 1: **Warehouse → Blacksmith** — 플레이어가 직접 옮기지 않아도 알아서 옮겨준다.
- 레일 2: **Blacksmith → SwordShop** — 자동으로 가져다 놓아준다.
- **두 소켓을 완성하면 게임이 끝난다.**

## 9. 아직 사용자가 말하지 않은 것 (물어봐야 하는 것)

구현하다 필요해지면 **추측해서 채우지 말고 물어본다.**

1. 각 건설 소켓의 **요구 개수** (나무 몇 개? Blacksmith는 나무·철 각각 몇 개? 레일은 코인 몇 개?)
2. 생산 소켓의 **게이지가 차는 데 걸리는 시간**
3. 일꾼의 **채집 속도** / 철 일꾼의 **광산 체류 시간** 기본값
4. 손님의 **등장 주기**, **칼 3개당 지불 코인 수**, 동시에 줄설 수 있는 **최대 인원**
5. 대장간의 **1회 제작 시간**
6. 적재 소켓별 **표시 최대 개수** 기본값
7. 레일의 **운반 주기·속도**
8. 게임 종료 시 **연출과 CTA**
9. 울타리 에셋 / green_bob 손님 에셋 / ironMine active 에셋 — **사용자가 제작해 알려줄 예정** (HQ 텍스처는 이미 있고 씬에 적용돼 있다)

### 🔴 `ScatterField`의 첫 배치는 `start()`에서 한다 — `onLoad`가 아니다 (2026-09-18 수정)

`제외를 씬 전체에서 수집`은 다른 노드의 `ScatterExclude`가 자기 `onEnable`에서 채우는 static
목록을 읽는다. 엔진은 노드를 **계층 순서대로** 활성화하므로 `onLoad` 시점에는 그 목록이

- 바깥 필드(`invertExclude` 꺼짐) → 제외가 없다고 보고 **건물 위에도 깐다**
- 안쪽 필드(`invertExclude` 켜짐) → 깔 영역이 없다고 보고 **한 그루도 안 깐다**

**에러도 경고도 없이 조용히 0이 된다.** 실제로 `TreeFieldDirt`가 0그루가 된 원인이 이것이었고,
`_rebuild()`를 `start()`로 옮겨 고쳤다(엔진이 씬의 모든 `onLoad`/`onEnable` 뒤에 `start()`를
보장하므로 계층 순서와 무관해진다). `ScatterField`는 씬 3에만 쓰여 씬 1·2 영향은 없다.

## 12. 손님 시스템 (2026-09-18 3차)

### 사용자가 정한 값 【확정】

| 항목 | 값 |
|---|---|
| 줄 간격 | **1m** |
| 줄 최대 인원 | **8명** |
| 1인당 구매 | 칼 **3개** |
| 1인당 지불 | 코인 **5개** |
| 판매 | **한 번에 1명만** |
| 퇴장 | **온 길을 되돌아간다.** 제자리에서 돌지 않고 **줄을 살짝 비켜서** 반대 방향으로 가서 **끝까지 간 뒤 사라진다** |

### 만든 것

| 파일 | 하는 일 |
|---|---|
| `Customer.ts` **(신규)** | 손님 한 명. "여기로 가라"만 듣고 `Player.moveDirOverride`로 걷는다. 상태 3종(자리로/맨앞/퇴장) |
| `CustomerSpawner.ts` **(신규)** | **줄과 판매를 통째로 관리.** 자리 계산·판매 순서·퇴장 경로가 전부 여기 한 곳에 있다 |
| `CoinGroundStack.ts` | `플레이어에게 돌려주기` / `플레이어에게서 받기` 추가 |

**줄 관리를 손님 개체에 두지 않은 이유**: 개체가 스스로 줄을 살피면 개체마다 다른 개체를 훑어
인원수의 제곱이 되고, **"한 번에 한 명만 판매"** 를 개체 쪽에서는 지킬 수가 없다.

**자리 계산**: `i번째 자리 = 줄 머리 + (등장 지점 쪽 방향) × (i × 간격)`. 배열 순서가 곧 자리
번호라서 **맨 앞이 빠지면 뒤 전원이 저절로 한 칸 당겨진다** — 밀어주는 코드가 따로 없다.

**퇴장 경로**: 줄 방향에 **수직으로** `퇴장 비켜서기`(0.9m)만큼 비켜선 뒤 등장 지점 쪽으로
되돌아가 그 자리에서 사라진다. 비켜서는 쪽이 항상 같아서 나가는 손님이 한 줄로 흐른다.
**0으로 두면 줄과 같은 선으로 돌아가 뒤에 서 있는 손님들을 뚫고 지나간다.**

**칼 넘기기**: `CoinGroundStack.transferOneTo(손님노드, null)` — 스택을 null로 주면 칼이 손님에게
날아간 뒤 **그대로 사라진다**(손님 등에 쌓이지 않는다). 일꾼의 "흡수만" 과 같은 방식이다.

### 🔴 적재 소켓은 방향이 있다 — 안 정하면 조용히 깨진다

`CoinGroundStack`은 원래 "쌓이고, 플레이어가 오면 돌려준다" 한 방향뿐이었다. 그래서 상점의 칼
무더기는 **플레이어가 놓는 순간 다시 빨려 들어가** 아무것도 쌓이지 않는다. 방향 두 스위치를 추가했다.

| 무더기 | 돌려주기 | 받기 | 왜 |
|---|---|---|---|
| `WarehouseStack_Wood` / `_Iron` | O | X | 일꾼이 채우고 플레이어가 가져간다 |
| `ShopStack_Sword` | **X** | **O** | 플레이어가 **가져다 놓는** 자리. 켜두면 놓자마자 되가져온다 |
| `ShopStack_Coin` | O | X | 손님이 채우고 플레이어가 줍는다 |

**둘 다 켜면 놓자마자 되가져오는 무한 왕복**이 된다. 기본값은 `돌려주기 O / 받기 X`로,
기존 씬은 영향이 없다.

### 씬 배선

| 노드 | 위치 | |
|---|---|---|
| `CustomerSystem` (Systems 아래) | — | `CustomerSpawner` |
| `CustomerQueueHead` | (-4.20, 4.00) | 맨 앞 손님이 서는 자리 (상점 앞) |

## 14. 레일 · 광산 상태 · 달구지 (2026-09-18 5차)

### 레일 — 경로는 **몬스터 러쉬 경로와 같은 `RushPath`**

사용자 지시: *"해당 path는 기존의 몬스터 경로를 설정한 것처럼 내가 직접 잡고 조정할 수 있어야 해."*
→ 경로 편집기를 새로 만들지 않고 **`RushPath`를 그대로 썼다.** 잡는 방법이 몬스터 경로와 완전히
같다 — 자식에 `Anchor0` `Anchor1` … 노드를 두고 씬 뷰에서 끌면 되고, 각 앵커 밑에 `Handle`을
두면 곡선이 되며, 곡선 미리보기도 그대로 나온다.

**`ResourceRail.ts`** (신규) — 한 컴포넌트가 **한 종류만** 옮긴다.
창고 → 대장간처럼 두 자원을 같은 길로 보내야 하면 **같은 노드에 컴포넌트를 두 개** 붙이고
둘 다 같은 경로를 가리킨다(목록 프로퍼티로 만들지 않은 이유: 배열은 MCP로 못 쓴다).
**옮기는 종류는 도착 무더기가 정한다** — 종류를 따로 적게 하면 두 군데가 어긋난다.

| 노드 | 컴포넌트 | 옮기는 것 | 해금 |
|---|---|---|---|
| `Rail1_WarehouseToForge` | `RushPath` + `ResourceRail` ×2 | 창고 나무 → 대장간 나무 / 창고 철 → 대장간 철 | 트리거 **5** |
| `Rail2_ForgeToShop` | `RushPath` + `ResourceRail` | 대장간 칼 → 상점 칼 | 트리거 **6** |

앵커는 각 레일에 3개씩 두었다(출발·중간·도착). **위치는 계산값이니 끌어서 맞춘다.**
기본값: 출발 간격 0.8초 / 이동 속도 3m/s / 띄우는 높이 0.45m / 자전 90°/s / 동시 최대 12개.

레일이 쓰는 새 공개 API 두 개: `CoinGroundStack.takeOne()`(하나 덜어내고 그 자리를 돌려준다),
`CoinPool.prefabFor(type)`(레일 위에 띄울 모양을 풀과 같은 것으로 가져온다).

### 광산 상태 — 텍스처만 갈아끼운다

사용자 지시: *"기존에 ironmine_inactive_left45_body 였던 텍스처를 ironmine_active_left45_body로
교체하기만 하면 돼."* → **`CardTextureSwap.ts`** (신규). 트리거가 오면 `TextureCard`의

### 15-5. 울타리 크기 배율 0.7 (사용자 지시)

*"일단 울타리 에셋의 스케일을 0.7정도로 줄여줘."*

**`기둥 크기 배율`만 내리면 기둥만 작아지고 가로대는 원래 높이·두께로 남는다.** 그래서
`FenceBuilder`에 **`울타리 크기 배율`(`fenceScale`, 기본 1)** 을 새로 넣었다. 이 값은 세 곳에 걸린다:

1. **기둥** — `울타리 크기 배율 × 기둥 크기 배율`로 균등 축소
2. **가로대의 높이·두께** — 그대로 곱한다
3. **칸 나누기 기준** — 🔴 한 칸의 실제 길이가 `기본 길이 × 배율`(3 × 0.7 = **2.1m**)로 줄어들므로,
   구간을 나눌 때 그 줄어든 길이로 다시 센다. **이걸 안 하면 0.7배로 줄인 칸을 3m 간격으로
   늘려 붙여 살이 성글어진다.**

가로대의 **길이 축(X)만** 구간에 맞춰 따로 정해진다(`구간 길이 / 칸 수 / 모델 길이`).

**실제 크기 (모델 AABB × 0.7)**

| | 원래 | 0.7배 |
|---|---|---|
| 기둥 높이 | 1.470 | **1.029m** |
| 기둥 폭 | 0.480 | 0.336m |
| 가로대 높이 | 0.400~1.140 | 0.280~0.798m |
| 가로대 두께 | 0.255 | 0.178m |

**칸 나누기 결과**: 연결 **29칸** / 기둥 12개 = 생성물 41개, 총 58.40m.
목표 길이(2.1m) 대비 **0.805 ~ 1.045** — 늘어난 칸이 하나도 없다(전부 같거나 살짝 촘촘).

### 🔴 사용자가 경로 점 12개를 전부 직접 옮겼다 (2026-09-18)

`Point0`~`Point11` **전부** 에디터에서 조정된 상태다. 개구부 폭도 바뀌었다
(광산 앞 6.088 → **3.323m**, 맵 하단 진입로 2.185 → **2.543m**, 북서 출구 3.432 → **2.952m**).

**이번 작업에서 내가 바꾼 것은 `fenceScale` 하나뿐이고 점은 하나도 건드리지 않았다.**
앞으로도 이 점들을 계산으로 덮어쓰지 말 것 — 전부 사용자가 눈으로 맞춘 값이다(절대 규칙 2).

## 16. 가지 못하는 공간 (2026-09-18)

*"씬1,2에서 했던 것처럼 건물, 울타리에 대해 '가지 못하는 공간'을 시각적으로 보고 조정할 수 있는
박스를 포함해서 기능 붙혀줘."*

**새 시스템을 만들지 않았다.** 씬 1·2가 쓰는 `VirtualWall`이 이미 그것이다 — 물리 엔진 없이
박스 판정만 하고, `외곽선 표시`를 켜면 **씬 뷰에서만** 반투명 박스가 보인다(Play/빌드에서는 숨김).
**박스 크기는 그 노드의 스케일 그대로다**(스케일 1 = 1m). 그래서 씬 뷰에서 평소처럼 끌어 늘리면
막히는 범위가 그대로 바뀐다 — 이것이 "보면서 조정"이다.

### 기존 부품에 모자랐던 것 3가지를 채웠다

| 문제 | 고친 내용 |
|---|---|
| `VirtualWall`은 `activate()`를 받아야 막는데, 그걸 부르는 건 `BuildingTrigger`뿐이었다. 처음부터 있는 것(기지·광산·울타리)은 막을 방법이 없었다 | **`시작부터 막기`**(`activateOnLoad`, 기본 false) 추가 |
| 건물 밖에 둔 박스는 그 건물이 설 때 맞춰 켤 방법이 없었다 | **`등장 트리거`**(`activateTriggerId`, 기본 None) 추가 |
| `BuildingTrigger`가 자식 벽을 **하나만**(`getComponentInChildren`) 켰다 — 두 번째 박스를 넣어도 조용히 안 막혔다 | `getComponentsInChildren`으로 **전부** 켠다 |

### 🔴 덤으로 고친 것 — 기즈모 박스가 씬에 저장되고 있었다

`VirtualWall`의 기즈모 노드에 `DontSave`가 없어서, **씬에 직접 놓은 벽은 그 박스가 씬 파일에
저장되고 빌드에도 실렸다**(안 보이는 노드 + 재질 참조가 벽 수만큼). 같은 프로젝트의
`EditorGizmoController`(RushPath·MapBounds가 쓴다)는 `DontSave`를 찍고 **매 프레임 다시 찍어**
이미 저장된 씬까지 청소한다 — `VirtualWall`만 그 관례에서 빠져 있었다. 같은 방식으로 맞췄다.
실측: 고치기 전 tycoon 씬에 기즈모 노드 **6개**가 저장돼 있었고, 고친 뒤 **0개**다.
(씬 1·2는 벽이 프리팹 안에 있어 원래 0개였다 — 그래서 여태 안 드러났다.)

### 건물 — 막는 박스 6개

각 건물의 **자식 `Block` 노드**에 `VirtualWall`을 붙였다(씬 1·2와 같은 구조).
크기의 출발값은 **사용자가 이미 조정해 둔 `ScatterExclude`**(나무 제외 범위)에서 가져왔다 —
"건물이 차지하는 자리"라는 뜻이 같아서 출발점으로 적당하다. **용도가 다르므로 눈으로 보고
따로 맞추면 된다.**

| 노드 | 부모 | 크기 (X×Z) | 막기 시작 |
|---|---|---|---|
| `Block` | `Warehouse` | 5.20 × 4.00 | 부모 `BuildingTrigger`(2) |
| `Block` | `WorkerLodge` | 4.00 × 4.00 | 부모 `BuildingTrigger`(1) |
| `Block` | `Blacksmith` | 4.00 × 4.00 | 부모 `BuildingTrigger`(4) |
| `Block` | `SwordShop` | 4.00 × 4.00 | 부모 `BuildingTrigger`(4) |
| `Block` | `ironMine` | 6.00 × 4.00 | **시작부터**(트리거 없는 건물) |
| `Block_HQ` | `Blockers` | 5.20 × 4.40 | **시작부터** |

`Block_HQ`만 부모가 건물이 아니다 — **HQ는 프리팹 인스턴스라 자식을 붙이면 `mountedChildren`으로
들어가 다루기 번거롭다.** HQ는 움직이지 않으므로 `Blockers` 노드 아래에 월드 좌표로 두었다.

### 울타리 — 구간마다 박스 하나

`FenceBuilder`에 **`통과 막기`**(기본 false)와 `막는 두께(m)`·`막기 여유 마진(m)`·
`막는 박스 보이기`·`막는 박스 재질`을 더했다. 켜면 **울타리가 선 구간마다 박스 하나**를 함께
만든다 — **비운 구간(출입구 3곳)에는 만들지 않으므로 거기로만 드나들 수 있다.**

칸마다가 아니라 **구간마다** 하나인 이유: 막힘 판정은 캐릭터마다 모든 박스를 도는 구조라
박스 수가 곧 프레임 비용이다(구간당 1개 = **9개**, 칸당이면 29개가 된다).

현재 값: 두께 0.6m / 마진 0.3m. **두께를 너무 얇게 주면 빠르게 움직이는 캐릭터가 한 프레임에
건너뛰어 통과한다.**

### 저장 확인

씬 파일에 저장된 `VirtualWall`은 **6개**(건물분)뿐이고 울타리 박스 9개는 `DontSave`라 안 들어간다.
박스 재질(`T_BlockGizmo.mtl`) 참조는 **7회**(건물 6 + FenceBuilder 1)로 정확하다.

재질은 씬 1·2가 쓰는 `texture/MapBoundsLine.mtl`을 **규칙 9대로 `tycoon/materials/T_BlockGizmo.mtl`로
복사**해 썼다(공유 자산을 씬 3이 직접 참조하지 않게).

### ⚠️ 알아둘 것 — 일꾼과 손님은 막히지 않는다

`Player.ts:225`의 막힘 판정은 **`joystickNode`가 연결된 캐릭터에만** 걸린다. 일꾼(`T_Worker`)과
손님(`T_Customer`)은 조이스틱이 없고 `moveDirOverride`로 움직이므로 **벽을 그냥 통과한다.**
지금은 오히려 편하다(일꾼이 최단거리로 다닌다). 막아야 한다면 그 조건을 손봐야 하는데,
**씬 1·2의 추종자 동작에도 영향이 가므로** 건드리지 않았다.

## 17. 울타리·막힘 문제 4건 수정 (2026-09-18)

### 🔴 1·2번은 **같은 버그**였다 — 울타리 박스가 전부 맵 원점에 쌓여 있었다

증상 둘: *"울타리 block 미작동"* + *"광산에서 shop까지 가로지르는 무언가가 block하고 있음"*.

`FenceBuilder._placeBlock`이 이 순서였다:

```
n.parent = this.node;          // ← 이 대입이 onEnable을 그 자리에서 부른다
n.setWorldPosition(...);       // ← 위치는 그 "다음"
```

`VirtualWall.activateOnLoad`가 켜져 있어서 **`parent =` 순간 `activate()`가 돌고**, 그때의
월드 좌표인 **원점 (0,0,0)** 이 굳어버렸다. 결과: 길이 3.5~9.9m짜리 박스 9개가 전부 맵 한가운데에
각기 다른 각도로 겹쳐 서 있었고(→ 맵을 가로지르는 정체불명의 벽), 정작 울타리 자리는 하나도
막히지 않았다.

**수정**: `activateOnLoad`를 쓰지 않고 **위치를 잡은 뒤 직접 `activate()`를 부른다.**
실측(수정 후): 박스가 `(0.05, −6.84)` 길이 5.34, `(6.54, −0.49)` 길이 6.18 … 로 구간을 따라간다.
원점에 있는 박스 **0개**.

> **교훈**: `addComponent` → `parent =` → `setTransform` 순서는 위험하다. `parent =`가
> `onEnable`을 동기 호출하므로, **변환에 의존하는 초기화는 위치를 잡은 뒤에** 해야 한다.
> (CLAUDE.md의 "`addComponent`는 활성 계층에 있으면 onLoad를 그 자리에서 부른다"와 같은 함정이다.)

### 3. 울타리가 대장간과 함께 나온다

`FenceBuilder`에 **`등장 트리거`**(기본 None)와 **`등장 지연(초)`** 을 더했다.
트리거 전에는 **보이지도, 막지도 않는다**(만들어만 두고 렌더러를 꺼둔다. 막기도 그때 켠다 —
아직 서지도 않은 울타리가 길을 막으면 안 된다).

씬 3: **트리거 4**(대장간) + **지연 1.3초**. 같은 트리거로 서는 것들과 순서가 이어진다:
대장간 0 → 상점 0.5 → ground_main 0.9 → ground_sub 1.1 → **울타리 1.3**.

**에디터에서는 트리거가 돌지 않으므로 항상 보인다** — 안 그러면 형태를 맞출 수가 없다.

### 4. 벽에 막히면 미끄러진다

예전 `Player`는 월드 X축, 그다음 Z축을 따로 시도해 막히는 축만 취소했다. 벽이 축에 나란하면
그게 곧 미끄러짐이지만, **벽이 45도로 놓이면 두 축이 동시에 막혀 제자리에 완전히 멈춘다** —
씬 3의 울타리가 −45도라 정확히 이 경우였고, *"꺼끌꺼끌한 표면에 걸린 느낌"* 이 여기서 나왔다.

**`VirtualWall.slideForPlayer()`** 를 새로 만들어 **막은 벽 자신의 축**으로 푼다. 벽을 파고드는
성분만 죽이고 벽을 따라가는 성분은 남긴다. 어느 면으로 들어갔는지는 **직전 위치의 로컬 좌표**로
판별하고, 모서리로 들어간 경우엔 더 깊이 파고든 축을 죽인다. 미끄러진 자리가 또 막히면
(구석) 그때는 멈춘다 — 더 밀면 벽을 통과한다.

**계산 검증** (한 프레임 0.12m, 80프레임 이동 거리):

| 진입 각도 | 45° 벽 기존 | 45° 벽 수정 | 축 정렬 벽 기존 → 수정 |
|---|---|---|---|
| 정면 | 0.84m | 0.84m | 0.84 → 0.84 |
| 살짝 비스듬히 | 0.95m | **3.36m** | 3.36 → 3.36 |
| 많이 비스듬히 | 1.20m | **7.98m** | 7.98 → 7.98 |
| 거의 나란히 | 8.84m | 9.52m | 9.52 → 9.52 |

🔴 **축에 나란한 벽에서는 네 경우 모두 수치가 완전히 같다 — 씬 1·2는 영향이 없다.**
그리고 수정 후에는 45° 벽의 결과가 축 정렬 벽과 정확히 같아진다(각도와 무관해졌다).

### 확인

`Fence` 자식 62개 = 점 12 + **막는 박스 9** + 연결 29 + 기둥 12. 전부 계산과 일치한다.

⚠️ **`scene_hierarchy get_hierarchy`는 위치·회전·크기를 돌려주지 않는다**(uuid·name·type·active만).
그걸 모르고 읽으면 모든 노드가 원점에 스케일 1인 것처럼 보인다 — 실제로 한 번 오판했다.
좌표 확인은 `node_query info`나 씬 JSON으로 해야 한다.
